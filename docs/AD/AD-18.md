# AD-18: The `:batch` engine host runs at default thread priority; only `:live` runs at background priority

| | |
|---|---|
| Status | Accepted |
| Decided | `2026-11-13 01:59 CET` |
| Decided by | Martin Hajný (@hajnina) |
| Drafted by | Claude (Sonnet), branch `fix/batch-engine-priority` |

## What
- The `:batch` engine host sets its binder thread to `THREAD_PRIORITY_DEFAULT` (nice 0) before every op, `Open` included, so the native pools (ORT, XNNPACK, LiteRT) inherit it and a reused binder thread that was lowered earlier is raised again.
- The `:live` host keeps `THREAD_PRIORITY_BACKGROUND` (nice 10) for `Open` and the embedder ops: it runs beside the recorder and the UI, which must stay smooth.
- The in-process host (`LocalEngineHost`) is untouched.
- The policy is one pure function, `EnginePriority.of(role, op)`, with a JVM test. Each `Open` logs one `host_priority` line with role, op and nice.
- `ModelDispatchers` (main process) stays at background priority: its threads only wait on binder calls, the compute runs in the host.

## Why
- Measured on a Pixel 8: all 22 threads of `:batch` sat at nice 10, the busy threads landed on little and mid cores while the big core idled, and batch transcription ran 3.5-3.7x slower than real time while the phone was in use (diarizer RTF about 1.5, Canary RTF about 1.8).
- The batch queue only runs when no recording is active (`canRun = !recordingActive`) and the user waits for the results, so background priority there buys nothing and costs a lot.
- Rejected: keeping background priority and accepting the slowdown; raising it only while charging (more complex for no benefit, since the queue never runs during a recording).
- Accepted cost: the batch work competes with foreground apps for CPU while it runs.
