# AD-11: No migrations and no compatibility code before the first release

## Context
- The app has no users. Every install is a test device the team controls; the data on it is test data ([AD-03](AD-03.md) made the same argument for speech models, and `AGENTS.md` says the QA build may be purged at any time).
- `MindStore` carried a ladder of schema steps (`onUpgrade` for versions 2 to 4: added columns, a name split, two tables), the deletion of two older databases (`LEGACY`), and a test with a fake version 1 database. Every schema change would have added another step, a backfill and a test, for data nobody needs to keep.
- PR 2 ([AD-10](AD-10.md)) changes the schema again (versioned segments, provenance columns).
- The session-summary branch adds its own table (its schema version 5). It collides with the same rule.

## Decision
1. **Until a later decision supersedes this one, no migrations are written.** The schema is one definition in the create path (`MindStore.SCHEMA`). `VERSION` is bumped whenever the schema changes, and a database of any other version is wiped and recreated (`onUpgrade` and `onDowngrade` drop every table and run `onCreate`). An old dev or QA database loses its data; models and the key file are not touched. Wiping by hand (erase, or `pm clear` on the QA build) does the same.
2. **Breaking changes are fine.** This covers the schema, on-disk formats (the audio chunk format, the key file, the wire format between the processes) and internal APIs. There is no backward-compatibility burden: no deprecation shims, no readers of an old format, no fallbacks for old data, no columns kept only so old rows still fit.
3. **Migration and compatibility code is not shipped before the first release, and is deleted when found.** Anyone who sees such code (a version step, an "old format" branch, a legacy name kept for old data) removes it in the change that finds it.
4. **Other open work follows the rule.** The session-summary branch puts its table into the create path, with no migration step. If it uses a schema version number, it rebases onto the current `VERSION`.
5. **When the first release ships, a new decision supersedes this one and introduces migrations.** At that point:
   - the schema of the release is frozen as the baseline (version 1 of the migrated line), and `VERSION` only goes up from it;
   - every later schema change comes with a migration step and a test that opens a database of the previous version and checks its data;
   - a database of an unknown (newer) version fails closed instead of being wiped;
   - on-disk formats and the internal wire format get a version field and a rule for reading the previous one.
   Until that decision is merged, this one stands.

## Alternatives considered
- **Keep writing migrations.** Rejected: dead weight with zero users. Each step needs code, a backfill and a test, and the unknown-provenance rules of AD-10 as first drafted existed only to carry old rows. The data they protect is test data.
- **Keep the existing steps and add none from now on.** Rejected: the old steps are already dead code on every device the team uses, and leaving them suggests an upgrade path that nobody tests.
- **Fail on a version mismatch (no wipe).** Simpler in code, but then every schema change needs a hand wipe on every test device before the app starts. Rejected: the wipe is five lines and the data is disposable.

## Consequences
- **Better:** a smaller and clearer `MindStore`; no migration tests; each schema change is an edit of one definition and a version bump.
- **Worse, accepted:**
  - every schema change wipes the local database of every test device, including its sessions, facts and queue;
  - the same would be true of a real user's data if the app shipped with this rule still in force, which is why point 5 exists.
- **Still true:** the vault key, the audio files and the models are outside the database and survive a wipe of it.

## Verification
- **Device test (CI):** a database of another version is wiped and recreated on open (`DataLayerTest`).
- **Review:** no version-step ladder, legacy-database reader or old-format code remains (`grep -rn -i "migrat\|legacy" app/src`); what was left in place and why is in the PR description.
