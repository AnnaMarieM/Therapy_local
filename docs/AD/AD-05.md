# AD-05: One pinned look: bundled static fonts, pinned font scale, weight and density, explicit colours, deterministic breakpoints

| | |
|---|---|
| Status | Accepted |
| Decided | `2026-11-06 23:40 CET` |
| Decided by | Martin Hajný (@hajnina) |

## Context
- The same QA build looked different on a POCO (Xiaomi 2510DPC44G, HyperOS, Android 16, 1156x2510 at 480 dpi, about 385 dp wide, system font scale 0.9) and on a Pixel 8 (about 411 dp) and a Samsung tablet (824 dp). Side by side (`/tmp/shots/side_by_side.jpg`), the wordmark "MnemoThera" is Fraunces Black, soft and low-contrast, and wraps to "MnemoThe / ra" on the POCO, and a light, high-contrast display cut on one line on the tablet.
- Fraunces was bundled as a variable font (axes `opsz` 9..144, `wght` 100..900, `SOFT`, `WONK`; master defaults wght 900, opsz 9, WONK 1). `Type.kt` selected the cut with `FontVariation.Settings`. A device that does not apply the settings draws the master default, which is exactly the heavy, low-contrast cut on the POCO. Whether HyperOS drops the settings or rebuilds the typeface through its own weight handling cannot be told from the code (see Verification).
- The system can also change the look without any app code: font scale (`Configuration.fontScale`; every size in the app is `sp`), bold text and the HyperOS font-weight slider (`Configuration.fontWeightAdjustment`, which Compose adds to the requested `FontWeight`, so a different face is matched), and the display-size setting (`densityDpi`, which moves every dp width, and so every breakpoint, with it).
- `PaperTheme` set only 9 of Material's 15 text slots; Material fills the others with `FontFamily.Default`, the system font (MiSans on HyperOS). Typed shapes (`●`, `○`, `■`) are in none of the bundled fonts and fell back to a system font.
- Colour: the manifest theme was the framework `Theme.Material.Light.NoActionBar`: no explicit window background, no `forceDarkAllowed`, and `enableEdgeToEdge()` with its automatic bar style follows the system dark mode (light icons on cream paper) and lets the system draw a contrast scrim behind the navigation bar. A ROM's own "dark mode for apps" or reading-mode tint is not controllable from an app.
- Layout: every breakpoint (`Adaptive`: Medium from 600 dp, Expanded from 840 dp; two panes when Expanded, or Medium and wider than tall) read `LocalConfiguration.screenWidthDp`, which the ROM computes at the user's density. Phones are locked to portrait (`R.bool.portrait_lock`); `values-sw600dp` unlocks. At 385 dp and 411 dp no breakpoint is crossed: both are Compact, one pane. The only element at the edge of the screen on a phone is the letter rail of the client reel, which shows whenever two or more first letters exist in the client list (`Home.kt`, `index.letters.size > 1`), so it depends on the data on the device, not on the device.
- The wordmark (`Gate.kt`) was a `Text` with no line limit at a fixed 64 sp, so any wider cut wrapped.

## Decision
1. **Fonts are static.** Each face the app uses is a static instance in `res/font` (`fraunces_display_260/380` and italics at optical size 144, `fraunces_text_340` and italic at optical size 24, `geist_400/500/600`, `geist_mono_400`), cut by `tools/make-static-fonts.py` from the variable masters kept in `tools/fonts-src`. `Type.kt` states weight and style for each, with no `FontVariation`. No text style uses a system family; a unit test (`TypeScanTest`) fails on `FontFamily.Default/SansSerif/Serif/Monospace/Cursive` in product code (the debug harness is exempt) and on any style or Material slot outside `Type.Bundled`. `paperTypography()` gives all 15 Material slots a bundled family. Glyph coverage: Latin, Latin Extended (all Czech diacritics) and general punctuation are in all three families; shapes are drawn (`LanguagePicker`) or removed (the `■` in the hold label).
2. **`DisplayPin`** is applied in every `attachBaseContext` (Application, MainActivity, both services). It sets `fontScale = 1`, `fontWeightAdjustment = 0` (not `UNDEFINED`: an undefined field does not override the system's value) and `densityDpi = DENSITY_DEVICE_STABLE`, and leaves the window dp (which follow rotation and split screen) to be converted by `pinnedDp`. One constant, `DisplayPin.ENABLED`, switches all of it off.
3. **Colour is explicit.** Theme `Theme.MnemoThera` (light, `forceDarkAllowed=false`, paper window and splash background, transparent bars with dark icons, contrast enforcement off, cutout mode `shortEdges`, ink accent and highlight); `Window.isForceDarkAllowed=false`; `enableEdgeToEdge` with light bar styles and no scrim; Compose `TextSelectionColors`, `LocalRippleConfiguration`, `LocalTextStyle` and the cursor brush set in `PaperTheme`/the text fields. No dynamic colour (never used).
4. **One breakpoint entry.** `Adaptive.layoutFor(widthDp, heightDp)` is the only source of class and pane decisions (table in its KDoc). The window width is converted from the system's dp to dp at the pinned density (`DisplayPin.pinnedDp`) before it reaches that function. `BreakpointTableTest` pins widths 360, 385, 411, 600, 840, 1200 in both orientations.
5. **The wordmark never wraps.** `OneLine` steps the size down until the text fits on one line.

## Alternatives considered
- **Leave the user's settings in charge.** Rejected by the owner's requirement that all users get the same look; it is also what produced the reports.
- **Cap instead of lock the font scale** (for example `min(fontScale, 1.0)`, or 1.15 as Material recommends). Rejected for now: it still leaves bold text and display size free, and the look would differ between a user at 0.9 and one at 1.0. `DisplayPin.pinned` is the one place to change if a cap is wanted later.
- **Per-OEM workarounds** (detect Xiaomi/Samsung and adjust). Rejected: unbounded, untestable without each ROM, and the fix for the cause (static fonts, pinned configuration) is the same for all.
- **Keep the variable fonts and verify the axes at run time.** Rejected: the failure is silent and ROM specific; a static face has nothing to apply.
- **Pin the dp width itself** (scale density so every phone is 411 dp). Rejected: it changes physical size per device (385 vs 411 dp phones differ in density by 7%) and is a larger change; breakpoints are already deterministic by width.

## Consequences
- Better: a face, size and weight that is the same on every ROM; breakpoints that do not move with the user's display settings; no ROM-dependent bar colours.
- Worse: the APK grows by about 0.9 MB of fonts (the masters are not shipped). A user who relies on large or bold system text gets neither inside this app. This is an accessibility regression for low-vision users, accepted by the owner for consistency; `DisplayPin.ENABLED` is the switch to relax it, and TalkBack and the screen magnifier still work. Layout in dp still differs between a 385 dp and a 411 dp phone (same class, slightly different widths); hero text scales with the window width.
- Accepted, still true: the ROM's own colour handling (HyperOS reading mode, colour scheme, per-app dark mode if it ignores `forceDarkAllowed`) and the Xiaomi "Sidebar" floating app drawer are outside the app; system bars, keyboard and dialogs drawn by the system keep the system font.
- `fontWeightAdjustment` is a Configuration field; if a future ROM applies weight outside Configuration, the static faces still cannot change weight in Compose except through the weight match, which the pinned value neutralises.

## Verification
- JVM: `TypeScanTest`, `BreakpointTableTest`, the existing `AdaptiveTest`.
- Instrumented: `DisplayPinTest` (pinned configuration and the resources of a derived context); the existing `AdaptiveLayoutTest` (pages at 320..1280 dp, both orientations) and `LayoutStabilityTest`, unchanged. A test that renders the whole screen at 360/385/411/600/840/1200 in the emulator lane was not added: the main screen needs the unlocked vault; the rule is tested through `Adaptive.layoutFor`, which is what `MindVault` calls.
- `scripts/build.sh full` green; `:app:compileQaKotlin` and `:app:compileDebugAndroidTestKotlin` compile.
- Device, not done at the time of writing: on the POCO the wordmark is the light cut on one line; `adb shell dumpsys activity activities` shows `fontScale=1.0` and `densityDpi=480` for the app; `adb shell settings get system font_scale` still 0.9 (the system setting is untouched, only the app ignores it).
