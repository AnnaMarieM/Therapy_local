# AD-15: Every pull request shows screenshots of all screens, built by CI and posted as a PR comment

| | |
|---|---|
| Status | Accepted |
| Decided | `2026-11-12 00:32 CET` |
| Decided by | Martin Hajný (@hajnina) |
| Drafted by | Claude (Sonnet), branch `docs/ad-15-pr-screenshots` |

## Context
- Reviewing a UI change today means reading Compose code or installing the APK on a device. Most changes in the current work (settings sheets, the add-client button, the summary format slider, the language switch) are visible changes that a reviewer cannot judge from a diff.
- The app has a QA build (`com.therapylocal.app.qa`) that holds test data only ([`AGENTS.md`](../../AGENTS.md)), a pinned look so rendering is deterministic ([AD-05](AD-05.md)), and an emulator CI that already builds the APK once and runs device lanes in parallel ([AD-13](AD-13.md)).
- GitHub has no API to upload an image into a comment. The repository is public, so a file pushed to a branch can be shown in a comment through its `raw.githubusercontent.com` URL, and anything pushed that way is public.

## Decision
1. **Every pull request that can change the UI gets screenshots of every screen of the app, on a phone and on a tablet profile, in one comment on the PR.** The comment is a single sticky comment, updated on each push, and names the commit it shows.
2. **The screenshots are made in CI**, on the emulator, from the QA build with seeded fake data. A real vault, real client data or a real recording is never shown, stored or published by this job. The seeding and the screen list live in the repository and follow the code: a new screen is added to the list in the change that adds it.
3. **The job runs beside the other device lanes** after the APK exists ([AD-13](AD-13.md)). It does not lengthen the critical path of a pull request and it is not a required check: if it fails or cannot post (a pull request from a fork has a read-only token), the pull request is not blocked, and the reason is in the job summary.
4. **The images are stored on a dedicated branch (`pr-screenshots`), never on a pull request's own branch or on `main`.** The comment points at them by commit. They are removed when the pull request closes, and an open pull request keeps only its latest few commits' images, so the branch stays small.
5. **Only that one job may write to the repository.** It has the narrowest permissions that allow pushing to the screenshots branch and commenting; no secret other than the workflow token is used.
6. **A pull request that cannot change what is drawn (docs only) does not run it.**

## Alternatives considered
- **Upload the images as workflow artifacts and link them.** Rejected as the only channel: artifacts are a download behind a click and expire, so nobody looks at them in review. They may still be kept as a backup.
- **An external image host or a preview deployment.** Rejected: a new service, a new secret and a new place where screenshots of the app live.
- **Screenshots committed into the pull request.** Rejected: binary noise in every diff and in the history of `main`.
- **Only the screens a pull request changes.** Rejected for now: knowing which screens a change reaches is itself error-prone, and a full set also catches a screen that an unrelated change broke.

## Consequences
- **Better:** a reviewer sees the UI of a change, on both sizes, in the pull request; a visual regression in an untouched screen is visible; the screen list is kept up to date by the people who add screens.
- **Worse, accepted:**
  - the screenshots are public, since the repository is: seeded fake data must stay obviously fake and free of anything that identifies a person;
  - one more emulator job per pull request (runner minutes do not matter here, [AD-13](AD-13.md); the concurrent-job cap does);
  - a screenshots branch that is cleaned by a workflow and can drift if that workflow fails;
  - a screen missing from the list is missing from the comment, so the list needs care.
- **Still true:** the existing checks gate merges exactly as before.

## Verification
- The first pull request that adds it shows its own comment, with images that load (checked by fetching the image URLs), a rerun updates the same comment and does not add another, and closing the pull request removes its images.
- The job's duration and the unchanged critical path of a full run are reported in that pull request.
