## Context

- [AD-08](AD-08.md) tries the GPU on every load and lets the guard and the two output proofs (`LlmProof`, `docs/MEMORY.md`, "Bad output fails the proof") decide whether it stays. The GPU binding is a plain `Backend.GPU()` (`LiteRtBindings.kt`) and the engine config sets no `activationDataType` (`LlmRunner.kt`), so LiteRT-LM uses the GPU's default activation precision.
- With that default, Gemma E2B gives wrong output on two of the three devices we test on: the Pixel 8 and the Galaxy Tab S7 (issue #48). The ladder then strikes the GPU and falls back to the CPU, which is 2.4× (Pixel 8) and 1.15× (tablet) slower in decode.
- LiteRT-LM's `EngineConfig` has `activationDataType`; `ActivationDataType.FLOAT32` was tried in the lab harness (`ProofLabActivity`) on 2026-11-07 on the Pixel 8 and is measured below on all three devices.

## Decision

We want FLOAT32. For **Gemma 4 E2B**, the LiteRT-LM engine config sets `activationDataType = ActivationDataType.FLOAT32` whenever the backend is the GPU, on every device.

- There is no device or SoC check: the backend ladder takes no device names into its choices (`docs/MEMORY.md`, "Accelerators and fallback").
- The CPU and NPU are unchanged. The embedder's GPU path is unchanged.
- Both output proofs stay as they are and are never weakened.
- E4B is not covered (see "Not covered").

### Why

- The default GPU precision fails proof 2 on the Pixel 8 and the tablet; FLOAT32 passes both proofs on all three devices, with identical replies across repeated runs.
- It costs nothing where the default already works: on the POCO F8 Pro decode speed is the same in both modes.
- It matters most on the Pixel 8: about 2.4× the CPU decode speed, against 1.4× on the POCO F8 Pro and 1.15× on the tablet.

### How they were run

- **When:** 2026-11-13, one night, host clock CET. Pixel 8 between about 03:15 and 03:35 (approximate), POCO and tablet matrix 03:36 to 03:42, E4B on the POCO 03:48 to 03:50 (CPU) and 03:59 to 04:01 (GPU).
- **App and library:** the QA build `com.therapylocal.app.qa`, LiteRT-LM `litertlm-android` 0.18.1 (`app/build.gradle.kts`). **The builds were not verified identical.** The Pixel 8 reported commit `c934eac1f11a`; the POCO and the tablet reported `commit: unknown` through the QA API. The tablet had the local `app/build/outputs/apk/qa/app-qa.apk` (SHA-256 `46e136b7f8f812789ba4944a888cff6cadd2b5e61ca98f1d2068a1386d69fb9e`) installed with `adb install -r` just before its run. Verification below re-runs everything on one recorded build.
- **Models:** `gemma-4-E2B-it.litertlm` (2 588 147 712 bytes) and, for the E4B rows, `gemma-4-E4B-it.litertlm` (3 659 530 240 bytes), as already on each device.
- **Harness:** `ProofLabActivity` (QA build only; main-process engine). It builds the `EngineConfig` itself: `maxNumTokens = 4096`, a fresh per-run `cacheDir`, and `activationDataType` unset (default) or `FLOAT32`. One engine per run, one new conversation per case, `ExperimentalFlags.enableBenchmark` for the speeds. Each run starts from a force-stopped app.
- **Sampling:** greedy: `topK = 1`, `temperature = 0.0`, `topP = 1.0`, seed 1, at most 400 output tokens. This is why repeated runs give identical replies.
- **Cases:** `facts4` (the shipped proof 1: a JSON array of four `{kategorie, text}` objects), `proof2` (the shipped proof 2: the app's extraction instruction on three made-up Czech sentences), `memprobe` (the #48 prompt; length only, no verdict). Verdicts come from the app's own checks (`LlmProof.check`, `LlmProof.checkFacts`).
- **Repeats:** each E2B configuration twice, each E4B configuration once. The POCO and tablet matrices ran at the same time, on separate devices, screen on.
- **Embedder:** `BackendProbeActivity`, `--es model embed --es backend GPU --ez force true --ei calls 5`: three fixed texts times five calls (15 calls), against a CPU reference run in the same probe.

| CPU | 10.3 s | 4.3, 6.4, 15.3 | pass | not recorded |

**The E4B CPU figures are unreliable.** Decode swung from 4.3 to 15.3 tok/s across the cases of one run, which a steady run would not do, and the phone was in use around that time. The CPU-to-GPU speed-up for E4B cannot be stated. An earlier GPU run that gave no result in 8 minutes happened while another app was in front of the probe: Android pauses a backgrounded probe, and the re-run in the foreground finished in under a minute.

### Not measured

- Peak memory of the engine host with FLOAT32 on E2B (only system free memory at samples, and for E4B on the POCO).
- Battery, heat and energy.
- A second run of E4B; E4B on the Pixel 8 or the tablet; FLOAT32 through the real ladder (every E2B run above was in the lab harness, forced).

## Alternatives considered

- **Keep the default and rely on the ladder.** Correct, but the Pixel 8 and the tablet lose the GPU and run Gemma on the CPU (5.9 and 13 tok/s).
- **FLOAT32 only on devices that fail.** Needs a device or SoC list, which the ladder deliberately has none of, and the POCO shows no cost from FLOAT32.
- **Try the default, retry with FLOAT32 after a failed proof.** Adds a full load (33 to 137 s on the Pixel 8) and a strike per device, for nothing FLOAT32 from the start does not give.
- **Skip the Gemma GPU on the tablet.** The gain there is only about 15%. That is a separate decision about the ladder and is not made here.

## Consequences

- **Better:** a correct Gemma on the Pixel 8's GPU at about 2.4× the CPU speed, and a correct GPU on the tablet.
- **Worse:** FLOAT32 uses more GPU memory (about 0.4 GB more at the sample for E4B on the POCO; not measured for E2B), and the Pixel 8's load stays at 33 s or more.
- **Accepted, still true:** the reply-quality limits above, and both proofs unchanged.

## Not covered

E4B is not covered until it is measured on the Pixel 8 and the tablet and its CPU baseline is re-measured on an idle phone. Until then E4B keeps the default GPU precision.

## Verification

1. Make the change in the production engine config (`LlmRunner.kt`), not the lab harness.
2. Re-run the E2B matrix above on all three devices on one build whose commit is recorded, unforced through the real ladder (`MemProbeActivity`), both proofs passing.
3. Measure the peak engine-host memory with FLOAT32 on each device.
4. A JVM test that the GPU `EngineConfig` carries `FLOAT32` and the CPU one does not.
