## Context
- [`docs/MEMORY.md`](../MEMORY.md) says: "The app gives no insights and writes no summaries. The app shows only the facts and each session's full transcript." The facts are quotes with a heading, never interpretation.
- The M1 plan asks for a last-session summary in a default clinical format (SOAP or similar), short paragraphs, that rebuilds when the therapist/patient roles are swapped. That is generated prose about a session, so it reverses the "no summaries" line.
- A session's facts are extracted window by window by Gemma 4 in `:batch` ([AD-01](AD-01.md), [AD-02](AD-02.md)); the same model, runner path (`Llm.ask` through `ModelPool`) and job queue can write the summary. No new model, process or runtime is needed.
- The roles of a session live in `speaker_maps`, one row per version ([AD-06](AD-06.md), [AD-07](AD-07.md)); the "Is this incorrect?" swap appends a version (`SpeakerMaps.appendSwap`). Utterances keep raw ids, so a text made with the roles in it is made from two inputs: the transcript and the map version.
- The benchmark for summarising long transcripts is not finished and the summary's length and style are undecided. The data layer (PR 2, [AD-10](AD-10.md), [AD-11](AD-11.md)) gives versioned transcripts, the provenance record and the stored stale flag, and says a summary reuses them. There are no migrations: the table is in the create path and the schema version is bumped.

## Decision
1. **The app may write one summary per session**, in a fixed default format (SOAP: Subjective, Objective, Assessment, Plan) in short paragraphs, from the stored transcript with its roles. It is shown for the last session of a client. It is a working note for the therapist, not a diagnosis; the prompts forbid inventing, diagnosing and advice.
2. **It runs as a job, `summary`, on the existing queue and model pool** (Gemma, text only, `:batch`). It is queued behind `window` of a new session and on demand ("regenerate"), is not a dependency of `commit`, and its failure never blocks the facts.
3. **One table, `session_summaries`, keyed by session**, stores the text and the method id with the `Provenance` columns of [AD-10](AD-10.md) (`Provenance.COLUMNS`: transcript hash, speaker-map version, prompt version (a hash of the prompt texts, the format and the limits), model, and the stored `stale` flag). `MindStore.refreshSummaryStale` sets the flag like `refreshStale` does for windows and facts, with the one addition AD-10 names: a summary is also stale when its speaker-map version is not the current one, since it names who said what. The roles swap appends a speaker-map version, refreshes the flag and queues a rebuild; the old text stays until the new one replaces it (written whole, not stale).
4. **The long-transcript method is behind one interface** (`SummaryMethod`). The method is **tree summarisation** (a pyramid, id `tree-v1`): everything is budgeted in tokens (`PromptBudget`) against the context the app already loads for its Gemma jobs (`MemoryConfig.LLM_MAX_TOKENS`, via `SummaryConfig.CONTEXT_TOKENS`), with room for the prompt and the reply. A transcript that fits one call is one call. Otherwise level 0 cuts the transcript, in order, into chunks that each fill one call and summarises each; level n+1 groups as many consecutive summaries as fit one call and summarises each group; this repeats until the rest fits one call, and that final call writes the summary. Roles stay in the text and order is kept. A piece over the budget on its own is split at word boundaries (nothing is dropped), the tree depth is bounded, and the counts are logged, never the text. The method id is stored with the summary, so a change of method or budget makes summaries stale. The method can be replaced without touching the table or the API.
5. **Format, prompts and length limits live in one place** (the format is one id, `SummaryConfig.FORMAT_ID`, `soap` the only registered one; it is part of the prompt version, and only the final call of the tree uses it, so the chunk and group levels do not depend on it; a later format choice needs no change to the stored shape) (`SummaryConfig` and `demo/prompts/summary.*.txt`), since they are an open product decision. Changing them makes earlier summaries stale; it does not need a new decision unless it changes what the app promises (point 1).
6. **Clinical text is never logged.** The job logs counts, model, prompt version and method id only.
7. [`docs/MEMORY.md`](../MEMORY.md) is updated to say the app writes this one summary and nothing else of the kind (no insights, no cross-session summaries, no advice).

## Alternatives considered
- **Keep "no summaries".** Safest for a clinical product (no generated prose that can be wrong). Rejected by the M1 plan: the therapist wants a quick recap of the last session.
- **Map-reduce over overlapping windows with a fixed window size of our own (the first version of this PR).** Rejected: it invented a window and merge size; the tree uses the context the app already loads.
- **A rolling (additive) summary.** Rejected: it is sequential, errors compound, and a long session cannot be resumed from the middle; the tree summarises each part independently.
- **Summarise the facts instead of the transcript.** Cheap, and every sentence traces to a quote. Rejected: the facts are about the client's life over months, drop what the therapist did and agreed, and cannot make a Plan section.
- **Its own provenance columns, as in the first version of this PR.** Rejected once PR 2 existed: one provenance shape on every derived item ([AD-10](AD-10.md)).
- **A separate process or a bigger model for summaries.** Rejected: one model per role ([AD-02](AD-02.md)); Gemma 4 E2B/E4B was chosen for the memory pipeline and the summary is the same kind of text work.

## Consequences
- **Better:** the therapist gets a recap that follows the roles they confirmed; a swap, a changed transcript or a changed prompt shows the summary as stale instead of silently wrong.
- **Worse, accepted:**
  - a generated summary can omit or mis-weigh something; the Assessment section comes closest to the "insight" the product avoided. It is stated as drawn only from the conversation, and the section can be dropped in `SummaryConfig.SECTIONS`;
  - every new session costs more LLM time: one call for a short session, about one per context-full of transcript plus the group levels for a long one;
  - a larger context may be needed for the summary job (`Pipeline.requiredContext` counts it);
  - the summary is stored in `mind.db` (encrypted, [SECURITY.md](../SECURITY.md)), deleted with its session, and is clinical content under the same rules as the transcript.
- **Stale needs the model and prompt version:** like the facts, the flag is recomputed where those are known (`SessionSummaryRepository`: when the summary is read and after a swap), not on every write. It is not part of `Reprocess.plan`; a summary rebuilds on swap and on the user's request, and is shown as stale otherwise.
- **Still true:** facts stay append-only quotes; the app shows no insights across sessions; no model other than Gemma writes text.

## Verification
- **Unit tests (JVM):** the tree with a fake model (one call when short; chunks, group levels and a final SOAP call when long; every word reaches a chunk; groups fill but never exceed the budget; bounded depth; an oversize piece is split and counted); the format id in the prompt version; prompt assembly (format and limits from `SummaryConfig`, roles written into the transcript); state none/generating/ready/stale; stale after a swap, a changed transcript, prompt or model; rebuild uses the new roles; retries and failures; English and Czech prompt files keep the same placeholders.
- **On-device (not done yet):** a real one-hour Czech and English session on E2B and E4B: time per summary, whether the context loads, and a reading of the output by a clinician against the transcript.
