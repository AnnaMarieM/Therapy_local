## Context
- A session has three inputs from which everything else is derived: the **audio**, the **raw transcript** (`segments`) and the **speaker map** (`speaker_maps`). Today only the speaker map is versioned and append-only ([AD-06](AD-06.md)). `MindStore.replaceSegments` deleted the session's segments and inserted new ones, so a changed transcript left no trace and nothing derived from the old text knew it was out of date.
- Derived items are `windows` (with embeddings), `facts` and, with PR 5, a session summary. `facts` has `llm_model` and `prompt_version`, written by `commit` and never read back (docs/MEMORY.md: "for debugging"). `windows` has only `embed_model`. Neither records which transcript it was made from or which speaker map was current.
- "Is this session stale?" is answered on demand by `jobs/Reprocess.kt`, per session, by comparing the `extract_cache` key (`prompt version|model|window text hash`) of every window. It is not stored, covers only extraction, and says nothing about a changed transcript or speaker map.
- docs/MEMORY.md says "Facts are append-only: a fact that changes over time is not updated", yet `replaceSessionFacts` deletes a session's facts and inserts new ones, which is also how a re-read after a language change works.
- Audio: `PendingAudio` encrypts each chunk while recording; the session's last job (`cleanup`) does not delete it but moves it to `retained/<session>/<recording>` and keeps it for `PendingAudio.RETENTION_DAYS` = 7 days (added 2026-11-02, "week-long audio retention"; debug and qa builds also export a wav). docs/MEMORY.md job step 5 and docs/SECURITY.md said audio is deleted by `cleanup`. The documents and the code disagreed.
- [AD-01](AD-01.md): the vault, the database and the queue live in the main process; engine hosts hold no key and open no database. Everything here is in the main process.
- Patient data is encrypted under one data key (DEK) and lives in one database `mind.db`. Martin has decided to keep both (see Alternatives).

## Decision
1. **The raw transcript is a versioned, append-only input.** New table `transcripts(session_id, version, sha256, source, segment_count, recording_id, audio_sha256, created_at)`. `segments` gets a `version` column, its primary key becomes `(session_id, version, idx)` and it references `transcripts`. `MindStore.appendTranscript` replaces `replaceSegments`:
   - `sha256` is `TranscriptHash.of(segments)`: SHA-256 over every segment's index, start, end, speaker and text, each part length-framed (`Prompts.hash`).
   - Content equal to the current version's hash writes nothing (a resumed or repeated transcribe job changes nothing). Different content is version n+1. Earlier versions and their segments stay as they were.
   - `source` is `diarized`, `chunks`, `import` (developer harness) or `migrated`.
   - Everything that reads the transcript (`segments`, `segmentsAround`, `transcriptLengthMs`) reads the latest version. `segments(session, version)` reads an older one.
2. **Inputs are immutable in the database, not only by convention.** A trigger refuses any `UPDATE` of `transcripts`, `segments` and `speaker_maps`. Deleting stays possible, as it is how a session or client goes (cascade).
3. **Audio is an immutable input referenced by hash.** The transcribe job stores `audio_sha256` (`AudioHash.of`: SHA-256 over the bytes `PendingAudio.encode` gives each chunk, in order; unknown, never a failure, when a chunk cannot be read) and the `recording_id` on the transcript version it produces, so a transcript can be tied to the exact audio, and retained audio can be found and checked, while that audio exists.
4. **Audio retention policy: the code is right, the documents are wrong.** Audio stays encrypted under the vault key in `audio/<recording>` until `cleanup`, then in `retained/<session>/<recording>` for 7 days, and goes sooner with its session, its client or an erase of the vault. This is what has shipped since 2026-11-02; nothing is extended. docs/MEMORY.md (job step 5) and docs/SECURITY.md are corrected to say so. The 7 days are a bounded debugging window, not a feature: a transcript can only be checked against the audio while it exists, and the stored hash proves which audio it was.
5. **One provenance mechanism for every derived item.** `Provenance(transcriptSha, speakerMapVersion, promptVersion, model)` and five columns, `prov_transcript_sha`, `prov_speaker_map_version`, `prov_prompt_version`, `prov_model`, `stale`, defined once (`Provenance.COLUMNS`) and added to every derived table. The kinds are listed in the enum `Derived(table, usesSpeakerMap)`; `windows` and `facts` today. Writing and comparing are generic: `Provenance.put`, `MindStore.refreshStale`, `Staleness.isStale`.
   - **windows:** transcript hash of the version they were cut from; speaker map current at the cut; "prompt version" is the cut configuration `MemoryConfig.WINDOW_CUT_VERSION` (window and overlap tokens); model is the embedder.
   - **facts:** transcript hash taken from the windows the facts were extracted from, speaker map current at commit, the extraction prompt version and model that were already stored (`prompt_version`, `llm_model`, which now are read back through the provenance). The old two columns stay (SQLite cannot cheaply drop them) and are written with the same values.
   - **A session summary (PR 5) adopts this mechanism:** one column set, one entry in `Derived` with `usesSpeakerMap = true` (a summary names who said what), `Provenance.put` on insert. It must not invent its own provenance columns. Until it merges the summary may keep a minimal record of its own; moving it over is a small follow-up, not a redesign.
6. **Stale is stored and computed from provenance.** `refreshStale(session, expected)` compares each derived row's provenance with the current inputs (the latest transcript hash, the latest speaker-map version for kinds that use it, and the prompt and model the caller names in `expected`) and sets or clears `stale`. It runs by itself when a transcript version or a speaker map is appended (transcript and map parts), and from the rebuild plan (prompt and model parts, which need the app context: language, chosen model).
   - A speaker-map change makes only kinds with `usesSpeakerMap` stale. Windows and facts do not: roles are resolved at read time and extraction reads the text only (`Pipeline.extractUser`), so a "Is this incorrect?" swap must not re-run the LLM.
   - **Unknown provenance is `unknown`, not stale.** Migrated rows keep what they have: facts get their model and prompt from `llm_model` and `prompt_version`; windows get their model from `embed_model` and an unknown prompt version (empty); the transcript hash and speaker-map version are filled in from the session's current ones (assumed to be what the row was made from: true for every row made before this change, as transcripts could not change and a swap did not re-run anything). A field that is empty or -1 never makes a row stale, only a known value that differs does. The alternative, marking everything stale, would offer a re-read of every session on the first start after the update.
7. **Rebuild re-queues stale items in order, and stays append-only.** `Reprocess.plan` refreshes the flags, then lists the sessions with a stale row (or, as before, a window whose `extract_cache` key no longer matches, which covers a session whose extraction produced no fact and so has no row to flag). `Rebuild.order` sorts them per client, oldest first, skipping sessions with open jobs; `Reprocess.start` queues each from the window job on, and the existing rule that a session is committed only after the client's earlier ones ([MEMORY.md D4](../MEMORY.md)) does the rest.
   - **How this fits "facts are append-only".** A fact is never edited in place: its heading, content, evidence and provenance do not change. The only column updated is `stale`, a computed flag. A stale fact is **superseded**: the rebuild writes the session's new facts and mentions, with their own provenance and `stale = 0`, and the old generation is removed in the same transaction (`replaceSessionFacts`, the behaviour it already had; its documentation now says it supersedes). Superseded generations are not kept: each would be more patient text and embeddings that every nearest-fact query must skip.
8. **Schema: one migration, version 5.** It creates `transcripts`; makes the existing segments of every session version 1 (`source = migrated`, hash computed during the migration; the table is rebuilt because the primary key changes); adds the five provenance columns to `windows` and `facts` and backfills them as in point 6; creates the immutability triggers. Fresh installs get the same schema from `onCreate`.
9. **Constraints.** No engine host reads or writes any of this; the hashes are computed in the main process, in the jobs that already run there. Hashes and versions go into logs, transcript text never.

## Alternatives considered
- **Per-patient keys (one data key per client, sealed under the vault key).** It would make deleting a patient a cryptographic erase: drop the key and every row, the WAL and any free page of that patient become unreadable. Martin rejected it and keeps the single DEK and the one-database rule. Costs accepted with that choice:
  - Deleting a patient is a row delete (`deleteClient` cascades). SQLite does not wipe the freed pages and the WAL keeps frames until a checkpoint, so deleted patient data can sit in `mind.db` and `mind.db-wal`, still encrypted under the same DEK, until the pages are reused. Anyone who has the DEK (so the unlocked app, or someone who got the password) can read that residue; an attacker without the DEK cannot.
  - **Cheap mitigations, not done in this PR because they cannot be verified off a device:** `PRAGMA secure_delete = ON` (zeroes freed content, a small write cost); a `wal_checkpoint(TRUNCATE)` after a delete; `VACUUM` after a delete (rewrites the whole file, seconds on a large database, and does not clear the WAL on its own). The first two are one line each but have to be tried against SQLCipher on a QA build (a `PRAGMA` that returns a row can fail through `execSQL`). A follow-up should do that and add a test that a deleted string is not found in the raw files. Until then the risk is accepted and stated in docs/SECURITY.md.
  - There is no way to hand one patient's data to someone else without exporting it.
- **Overwrite the segments in place and keep only a hash of the old ones.** Keeps the table small, but then derived items cannot be shown to come from text that no longer exists, and a rebuild could not be compared with what it replaces. Rejected: versions are rare (a re-transcription), so the cost of keeping them is small.
- **A separate `provenance` table that derived rows point to.** One place for the fields, but a row's staleness depends on its own session's current inputs, so the flag cannot live on a shared row, and every read would join. Rejected for columns defined once in code (`Provenance.COLUMNS`) and written and compared by shared functions.
- **Mark all migrated items stale.** Simple and strict, but offers a full re-read (hours on a phone) on the first start for sessions nothing is wrong with. Rejected; see point 6.
- **Keep superseded fact generations, with a `superseded_by` column.** Would make "append-only" literal and give a history of what an older prompt said. Rejected for now: more sensitive data kept, and every query that reads facts (nearest facts, mentions, session delete with promotion) would need to skip them.
- **Delete audio at `cleanup`, as the documents said.** The stricter policy and a one-line change (`finishAudio` deletes instead of retaining). Rejected only because it takes away a shipped capability silently in a data-layer change. It is Martin's call; if he prefers it, a later decision supersedes point 4 and the retention code goes.
- **Make a speaker swap stale the facts.** Rejected: it would re-run the LLM for nothing, as extraction reads only the text (point 6).

## Consequences
- **Better:**
  - the raw transcript cannot change silently; a change is a new version with its own hash, and the old one is still there;
  - every window and fact says what it was made from, and "is it up to date" is a stored flag the UI and the rebuild can read instead of a recomputation per session;
  - one change of config (prompt, model, cut size, embedder) or of input finds exactly the items it affects;
  - the audio policy in the documents is what the code does;
  - a summary can adopt the same provenance by listing itself in `Derived`.
- **Worse, accepted:**
  - a re-transcription keeps the old text next to the new (patient text twice; they go with the session);
  - the migration rebuilds `segments` once (copy of every row, in one transaction);
  - `facts` keeps `llm_model` and `prompt_version` next to `prov_model` and `prov_prompt_version`;
  - the hash of the audio reads every chunk once more after transcription;
  - deleting a patient is a row delete with possible free-page and WAL residue (see Alternatives).
- **Still true:** one DEK, one database, no engine host touches either ([AD-01](AD-01.md)); a merged decision is changed only by a later one; a fact is not edited.

## Verification
- **JVM unit tests (run in CI, and locally where the toolchain allows):** `TranscriptHash` (same input same hash, any change changes it, parts are length-framed); `TranscriptVersions.plan` and the append-only behaviour (same content writes nothing, a change is the next version, the old version is untouched, going back is a new version); `AudioHash` (order, content, unknown on a missing chunk); `Staleness` (each field, unknown never stale, speaker map only for kinds that use it); `Rebuild.order` (per client, oldest first, busy sessions skipped); `TranscribeFlow` stores the version with its source and audio hash and survives an unreadable chunk.
- **Device tests (`androidTest`, CI emulator):** a version 4 database opens at version 5 with every session's transcript as version 1, a correct hash, windows and facts with provenance and no stale flag; the triggers refuse an update of a segment, a transcript and a speaker map; a second `appendTranscript` with the same content adds no row, a different one adds version 2 and flags the session's windows and facts stale; a speaker swap flags nothing for windows and facts; deleting the session removes all versions; `Reprocess.plan` returns the stale sessions oldest first.
- **Not verified here:** SQLCipher itself (the migration SQL was run against stock SQLite 3.46, including the triggers and the cascades, but not through SQLCipher), the Pipeline on a device, and any of the secure-delete mitigations.
