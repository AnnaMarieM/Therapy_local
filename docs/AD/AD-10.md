## Context
- A session has three inputs: the audio, the raw transcript (`segments`) and the speaker map (`speaker_maps`). Only the speaker map was versioned and append-only ([AD-06](AD-06.md)). `MindStore.replaceSegments` deleted and re-inserted the segments, so a changed transcript left no trace and nothing derived from the old text knew it was out of date.
- Derived items are `windows`, `facts` and, with PR 5, a session summary. `facts` had `llm_model` and `prompt_version`, never read back; `windows` had only `embed_model`. Neither says which transcript it came from.
- "Is this session stale?" was answered on demand by `jobs/Reprocess.kt` from the `extract_cache` key. That is not stored and covers only extraction.
- docs/MEMORY.md says "Facts are append-only", yet `replaceSessionFacts` deletes a session's facts and inserts new ones.
- Audio: `PendingAudio` encrypts each chunk while recording; the session's last job (`cleanup`) moves it to `retained/<session>/<recording>` for `RETENTION_DAYS` = 7 (shipped 2026-11-02). docs/MEMORY.md step 5 and docs/SECURITY.md said it is deleted there. Code and documents disagreed.
- [AD-01](AD-01.md): vault, database and queue stay in the main process; engine hosts hold no key and open no database.
- Martin keeps the single data key (DEK) and the one database. The schema rules of [AD-11](AD-11.md) apply: no migrations, the create path holds the schema.

## Decision
1. **The raw transcript is a versioned, append-only input.** Table `transcripts(session_id, version, sha256, recording_id, audio_sha256, created_at)`; `segments` gets a `version` column and belongs to a transcript version. `MindStore.appendTranscript` replaces `replaceSegments`. `sha256` is `TranscriptHash.of(segments)` (SHA-256 over index, times, speaker and text, length-framed with `Prompts.hash`). The same content as the current version writes nothing; different content is version n+1 and the old version stays. `segments`, `segmentsAround` and `transcriptLengthMs` read the latest version; `segments(session, version)` reads an older one. Nothing in the code updates a transcript or segment row.
2. **Audio is an immutable input referenced by hash.** The transcribe job stores `AudioHash.of` (SHA-256 over the bytes `PendingAudio.encode` gives each chunk, in order; null if a chunk cannot be read, never a failure) and the `recording_id` on the version it produces, so a transcript is tied to the exact audio and retained audio can be found and checked while it exists.
3. **Audio retention: the code is right, the documents were wrong.** Audio is encrypted under the vault key in `audio/<recording>` until `cleanup`, then in `retained/<session>/<recording>` for 7 days, and goes sooner with its session, client or a vault erase. Nothing is extended; docs/MEMORY.md and docs/SECURITY.md now say so.
4. **Provenance on derived items, one shape.** `Provenance(transcriptSha, speakerMapVersion, promptVersion, model)`, written into the columns `prov_transcript_sha`, `prov_speaker_map_version`, `prov_prompt_version`, `prov_model` plus `stale` (`Provenance.COLUMNS`) on `windows` and `facts`. The old `facts.llm_model` and `prompt_version` are dropped; the provenance columns replace them.
   - windows: transcript hash of the version they were cut from, speaker map current at the cut, the cut configuration (`MemoryConfig.WINDOW_CUT_VERSION`) as prompt version, the embedder as model;
   - facts: the current transcript hash and speaker map at commit, the extraction prompt version and model.
   - **A session summary (PR 5) reuses these same columns** (`Provenance.COLUMNS`, `Provenance.put`) rather than its own, and adds the rule that a speaker-map change makes a summary stale (it names who said what). Until it merges it may keep a minimal record of its own.
5. **Stale is stored.** `MindStore.refreshStale(session, table, promptVersion, model)` sets `stale` on the session's rows of `windows` or `facts` when their transcript hash differs from the current transcript, or their prompt version or model from the ones given. It is recomputed by the rebuild plan (the prompt and model need the app context); it is not flagged on every write. The speaker-map version is stored but not compared: roles are resolved at read time and extraction reads text only (`Pipeline.extractUser`), so a speaker swap must not re-run the LLM.
6. **Rebuild keeps "facts are append-only".** `Reprocess.plan` refreshes the flags and lists sessions with a stale row or an `extract_cache` key that no longer matches (the latter covers a session whose extraction gave no fact, which has no row to flag), per client oldest first, which is the order `sessions()` already returns. `Reprocess.start` queues them from the window job on; MEMORY D4 commits them in order. A fact is never edited: a stale generation is **superseded**: `replaceSessionFacts` removes the session's facts and mentions and inserts the new ones, with new provenance and `stale = 0`, in one transaction. Superseded generations are not kept (more patient text, and every fact query would have to skip them).
7. **Schema.** All of it is in the create path ([AD-11](AD-11.md)): no `onUpgrade` step, no backfill, no "unknown provenance". An existing database of the previous version is wiped and recreated on open.
8. **Constraints.** No engine host reads or writes any of this; hashes are computed in the main process, in the jobs that already run there. Hashes go into logs, transcript text never.

## Alternatives considered
- **Per-patient keys (one data key per client, sealed under the vault key).** Deleting a patient would be a cryptographic erase. Martin rejected it and keeps one DEK and one database. Costs accepted:
  - Deleting a patient is a row delete (`deleteClient` cascades). SQLite does not wipe freed pages and the WAL keeps frames until a checkpoint, so deleted data can remain in `mind.db` and `mind.db-wal`, encrypted under the same DEK, until the space is reused. Whoever holds the DEK can read it; an attacker without it cannot.
  - Cheap mitigations, not done here because they cannot be verified off a device: `PRAGMA secure_delete = ON`, `wal_checkpoint(TRUNCATE)` after a delete, `VACUUM` (rewrites the whole file, does not clear the WAL by itself). A `PRAGMA` that returns a row can fail through `execSQL` on SQLCipher, so a QA device has to try them, with a test that a deleted string is not found in the raw files. The risk is stated in docs/SECURITY.md.
- **Overwrite segments in place and keep a hash of the old ones.** Smaller, but derived items could not be shown to come from text that no longer exists. Rejected: versions are rare.
- **A shared `provenance` table, or a generic mechanism (a `Derived` kind list, an expectation type, a rule class).** Rejected as more machinery than the two real users need; a flag is per row and per session, so it cannot live on a shared row.
- **Triggers that refuse updates of inputs.** Rejected: nothing updates them, the code is the guard.
- **Keep superseded fact generations (`superseded_by`).** Literal append-only, but more sensitive data and every fact query would need to skip them.
- **Delete audio at `cleanup`, as the documents said.** The stricter policy and a one-line change, but it removes a shipped capability inside a data-layer change. Martin's call; a later decision can supersede point 3.
- **Make a speaker swap stale the facts.** Rejected: it would re-run the LLM for nothing.

## Consequences
- **Better:** the raw transcript cannot change silently and keeps its history; every window and fact says what it was made from, and "is it up to date" is a stored flag; a config or input change finds exactly the items it affects; the audio policy in the documents is what the code does; a summary reuses the same columns.
- **Worse, accepted:** a re-transcription keeps the old text next to the new (they go with the session); the audio hash reads every chunk once more after transcription; deleting a patient is a row delete with possible residue (see Alternatives); the existing database of a test device is wiped (AD-11).
- **Still true:** one DEK, one database, no engine host touches either; a fact is not edited.

## Verification
- **JVM tests:** `TranscriptHash` (stable, any change changes it, parts are framed), `AudioHash` (order, content, unknown on a missing chunk); `TranscribeFlow` stores the transcript with the audio hash and survives an unreadable chunk.
- **Device tests (`DataLayerTest`, CI):** same content appends nothing, a change is the next version and the old one is intact; deleting the session removes all versions; a new transcript version makes windows and facts stale until they are rebuilt; another prompt or model makes facts stale and a return to it clears the flag; a database of another version is wiped.
- **Not verified here:** SQLCipher itself, the pipeline on a device, `Reprocess.plan` (needs the app context), and the secure-delete mitigations.
