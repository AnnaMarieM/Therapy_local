## Context

All models run inside the app's own process today:
- Gemma 4 for the memory pipeline (`memory/MemoryLlm.kt`);
- EmbeddingGemma for live cues, search and the pipeline (`embed/Embedder.kt`);
- Canary and Whisper on sherpa-onnx (`asr/`).

[PR #42](https://github.com/AnnaMarieM/Therapy_local/pull/42) made loading graceful:
- `BackendLadder` tries NPU, GPU, then CPU and catches whatever a backend throws.
- `BackendGuard` remembers per phone what was attempting, proven or blocked.

Three failures cannot be caught in the same process, and they take the whole app down (the UI, a recording, the open vault):
- **The low-memory killer.** On a phone the GPU takes the model's memory from shared RAM, where Android cannot reclaim it. Measured: E4B took 3,469 MiB for a 3,490 MiB file (`AppConfig.kt`, `MemoryConfig`). On Mali/Tensor phones, OpenCL inflates graphics memory by 4+ GB (`DeviceMemory.kt`). `lmkd` then sends `SIGKILL`.
- **Native crashes.** GPU drivers, LiteRT-LM and ONNX Runtime are C++. A driver bug or a corrupt model file ends in `SIGSEGV`/`SIGABRT`.
- **Hangs.** A driver can deadlock in `initialize()`.

`BackendGuard` can only recover such a crash on the next start. So the first crash on a phone, and with a backend never proven there the second, still closes the app in front of the therapist.

Facts from the code that shape the decision:
- The pipeline only talks to the `Llm`, `Embed` and `Asr` ports (`jobs/Ports.kt`), through `ModelPool`. The end-to-end tests already replace them with fakes (D5).
- Live cues send up to about 320 s of 16 kHz PCM per tick (`LiveCueConfig.MAX_LOOKBACK_S`), about 10 MB. That is far over Binder's 1 MB transaction limit.
- `Vault.lock()` locks by killing its own process.
- `App.onCreate` runs in every process of the app and loads SQLCipher.
- No job runs while a session records (D3), so the live models and the pipeline models are never needed at the same time.
- Instrumented tests run in the app's main process, on an API 34 x86_64 emulator, with no model files. Both native engines ship x86_64 libraries.

## Decision

**Every model runs in a separate process. The app's main process never loads a model.**

1. **Two processes**, both running the same bound, non-foreground `EngineHostService`. The bind intent sets the role, which limits the models a process may load.
   - **`:live`** serves live cues and search: EmbeddingGemma with its audio encoder.
   - **`:batch`** serves the session pipeline: Gemma (and Gemma speech recognition), the text embedder, and Canary/Whisper.

   A pipeline crash can never take live cues down, and the other way round.
2. **The inference processes are stateless model servers.**
   - They hold no vault key, open no database, and write nothing patient-related to disk.
   - They do hold prompts and audio in memory while they work; that memory ends with the process.
3. **Everything else stays in the main process:**
   - the queue and `JobRunner`;
   - `ModelPool` and its one-model-at-a-time rule;
   - the vault and the database;
   - `BackendLadder` and `BackendGuard`, the per-device records, and the settings screen.
4. **One ladder attempt is one remote call.** The main process calls `open(model, backend, …)` on the host for each candidate. If the host dies during the attempt, the call fails with `DeadObjectException`, which the ladder already catches. The main process then:
   - records the strike immediately, with the exit reason it reads at once from `ApplicationExitInfo` for that pid (killed for memory, native crash, ANR);
   - restarts the host with backoff;
   - tries the next backend.

   Recovery on the next start remains only for the rare death of the main process itself.
5. **Proxies implement the existing ports.** `ModelPool`, `JobRunner`, `LiveCues` and search keep their code. Each proxy carries the generation of the connection it was made on. After a death every proxy reports `healthy = false`, and the existing reload path loads again.
6. **Large data does not go through the Binder parcel.** Audio crosses in `SharedMemory`. Prompts, replies and 768-float embeddings are small and go inline.
7. **Lifecycle.**
   - The main process binds `:batch` while `MemoryService` processes. It binds `:live` while live cues run or a search is open.
   - A host with no client stops after an idle timeout (about 2 min, in `AppConfig`). Ending the process is the most complete unload: GPU buffers, driver leaks and fragmentation all go with it.
   - Before `:batch` loads anything, `:live` is shut down and its death awaited. This replaces `Engines.suspend()` across processes, so `:batch`'s free-memory check never counts memory held by `:live`.
   - A host links to its client's death and exits as soon as the main process dies. Locking the vault therefore also ends every inference process.
8. **`App.onCreate` branches on the process name.** In `:live`/`:batch` it sets up logging only: no SQLCipher, no vault, no start-up recovery, no UI configuration.
9. **Logging.**
   - Each inference process writes its own file, `engine-live.log` or `engine-batch.log`: the same rotation, and lines flushed before every native step. Two processes appending to one file would interleave and break rotation.
   - Every line carries `proc=` and the `load_id` the main process sent, so the files read as one story.
   - The main process logs `engine_died`: the generation, the call in flight, the exit reason and memory before the death.
   - The log export bundles all files.
10. **Fallback and tests.** `LocalEngineHost`, which runs in-process, stays behind the same Kotlin `EngineHost` interface. Unit tests use it; it's also an emergency switch.

## Alternatives considered

- **Keep inference in the app process (status quo after PR #42).** Rejected. The first crash on each phone still closes the app; the guard can only make sure it does not happen again.
- **An inference process that takes jobs from the queue itself.** Rejected. The vault key would live in the process that crashes most often. Two processes would write the encrypted database. Locking would have to coordinate two processes holding decrypted data.
- **One shared inference process for live cues and the pipeline.** Simpler and lighter, but rejected by the decider. A pipeline crash must never affect live cues, and the extra process only exists while it is used.
- **A native signal handler in the app process.** Rejected. After `SIGSEGV` the process state cannot be trusted, and `SIGKILL` cannot be handled at all.
- **Keeping the hosts warm while the app runs.** Rejected in favour of the idle timeout. A warm host keeps gigabytes of model memory from the rest of the phone, and the system may kill it anyway.

## Consequences

**Better**
- The app never closes because of a model. A crash becomes a delay: a job retried on the next backend, or a pause in live cues.
- Strikes are recorded at the moment of the crash, with the system's exit reason, not on the next start.
- Unloading is complete. Patient text in model memory ends with its process.

**Worse, accepted**
- About 30–60 MB more RAM for each inference process that runs. They rarely both exist: `:live` stops when `:batch` starts.
- One IPC per prompt, embedding or transcription, which is negligible next to inference time.
- The first use after an idle stop pays a process start (about 100–300 ms) plus the model load.
- More code: AIDL, the service, the connection, and a process-aware `App`.

**Still true**
- An inference process can still be killed, even on the CPU. A model that is killed there again and again must fail its job as "too large for this phone" (and suggest E2B) instead of looping. `model_too_large_for_device` already detects it.
- Under extreme pressure `lmkd` can still kill the main process. That is less likely than today, because the inference process is the bigger target at the same priority.

## Requirements on the implementation

These come from mapping every call site of the engines. The implementation must keep them true:
- **Errors keep their meaning across the boundary.**
  - Binder only carries a few exception types. The host returns failures as a result: type name, message and cause types.
  - The proxy throws an equivalent exception again, because callers depend on them:
    - `Pipeline.embedFitting` splits a text only when the message says "exceeds maximum";
    - `JobRunner` records the exception's simple name as the failure code;
    - `ModelSwitched` and `JobStopped` are matched by type.
  - Messages from text-handling calls stay redacted in the logs, as today.
- **Measurements come back with the answer.** `MemoryLlm.ask` feeds `PerfStats.call` with LiteRT's benchmark numbers, and the UI reads them for time-left estimates. The host returns those numbers with every reply, and the main process records them.
- **Settings are passed in, not read in the host.** The debug backend override (`BackendPolicy.override`) lives in the UI process, and so does the choice of speech engine. Both travel with the `open` request.
- **Process-global native flags stay per process.** LiteRT-LM's `ExperimentalFlags` are global per process. With the LLM alone in `:batch`, the constrained-decoding toggle in `ask` and `GemmaAsr` can no longer leak into the live embedder.
- **Exit reasons are read per process.** The guard's `lastExit` takes the newest exit of any process today. It must filter by process name: a `:batch` death is not a main-process death.
- **Probes measure the right process.** `MemProbeActivity` (qa) measures the memory of its own process. It must either run its model in-process through `LocalEngineHost`, or ask the host for its memory.
- **Audio sizes.** By default a live-cue tick carries 20 s of audio (640 KB). A transcription chunk is 20 s (640 KB) and a voice query at most 20 s. Users can raise the live-cue lookback to about 327 s (10.5 MB). Audio always goes through `SharedMemory`, so no size ever meets Binder's 1 MB limit, which all transactions of a process share.

## Verification

- **Unit tests.** The ports, `ModelPool` and the ladder are unchanged. New JVM tests drive the connection's death handling through a fake host that "dies" mid-call: generation, strike, restart, backoff, too-large handling.
- **Instrumented test on the CI emulator.** A debug-only `crashForTest(kind)` on the host aborts natively, runs out of memory, or hangs. The test asserts that:
  - the test's own process (the app's main process) is still alive;
  - the job is retried and the guard shows the strike with the right exit reason;
  - the logs read `engine_died` → `backend_failed` → `ladder_done`.

  It needs no model files.

## Delivery

One PR, in four commits that each build green:
1. `EngineHost` interface and `LocalEngineHost`, with the engine code moved behind it. No behaviour change.
2. `EngineHostService` in `:live` and `:batch`: AIDL, `SharedMemory` audio, process-aware `App`, per-process logs.
3. `EngineConnection`: death detection, exit-reason lookup, immediate strikes, restart and backoff, `:live` shutdown before `:batch`, idle stop.
4. Crash-injection tests, docs (MEMORY.md, LOGGING.md), and the engine process state on the settings screen.
