# AD-16: The QA build has a control API for adb; no other build has it

| | |
|---|---|
| Status | Proposed |
| Decided | `pending` |
| Decided by | `pending` |
| Drafted by | Claude (Sonnet), branch `docs/ad-16-qa-control-api` |

## Context
- The QA build (`com.therapylocal.app.qa`) is the build we drive from adb: password-only unlock, screenshots allowed, test data only ([`AGENTS.md`](../../AGENTS.md), the QA/customer table in the `build-and-deploy` skill).
- Driving it today means a mix of UI taps, `qa/*.sh`, the e2e device runner and the debug harness (`DevHarness`, `DevResults`). Seeding clients, importing a recording, waiting for the pipeline and reading the result each need a different trick, and the UI taps break whenever the UI changes.
- The phone we test on also carries the real app (`com.therapylocal.app`), which may hold a real vault. Anything we add for testing must be unable to reach it.
- This is a therapy app. A door into the app for testing is a security decision, even when it is limited to a test build.

## Decision
1. **The QA build exposes one control API for adb. It exists in the QA build only.** It is compiled from the `qa` source set, is absent from `release`, `debug` and `feel`, and the customer build gains no exported component, permission or intent filter. The `build` job verifies on every pull request that the release APK and its merged manifest contain no trace of it (inside the existing APK and build jobs, so the critical path does not grow, [AD-13](AD-13.md)).
2. **The transport is an exported content provider, called through `adb shell content call`.** It accepts a call only from the adb shell user (the caller's uid is checked on every call); every other app on the device is refused. Results are JSON, small ones returned in the call and large ones written to the app's own external files folder (`.../files/api/`) for `adb pull`. Each result carries `api_version` and, on failure, an error code and a message.
3. **There is no network surface.** No socket, no HTTP server, nothing reachable from another device or another app.
4. **The commands cover what a test run needs:**
   - `status`: locked or unlocked, models present or downloading, the job queue, the build commit.
   - `setup` and `unlock` with the QA password.
   - `seed_clients`: the mock clients of the test corpus, idempotent.
   - `import_session`: an audio file on the phone, for a client and a language, run through the normal pipeline.
   - `wait`: until the job queue is idle, with a timeout.
   - `results`: the existing `DevResults` JSON (segments with speaker ids and role labels, the speaker map versions, facts with spans, times and speaker, the summary with its format and stale flag).
   - `swap_roles` and `set_summary_format`: the same actions as the UI.
   - `reset`: wipes the QA vault data and never the downloaded models.
   Each command calls the same code as the UI; none adds behaviour of its own.
5. **While the vault is locked, only `status`, `setup` and `unlock` work.** The standard QA password is documented and is used only here. Any command that deletes data refuses to run unless the application id ends in `.qa`.
6. **Clinical text is never logged.** Commands log their name, a result code and counts only ([`docs/LOGGING.md`](../LOGGING.md)). Results go to files, not to logcat. The QA build holds test data only, and this record does not change that rule.
7. **One host client, one document.** `qa/qa-api.sh` (bash, the system `adb`, `-s <serial>`) wraps every command; `docs/QA_API.md` lists each command with an example; the e2e device runner uses the same calls. A new feature that a test run needs adds its command in the same change.

## Alternatives considered
- **A loopback HTTP server in the QA app, reached with `adb forward`.** Convenient, but every app on the phone can connect to `localhost`, so the shell-user check of point 2 would have to be rebuilt as a token. Rejected.
- **Keep driving the app by UI taps and the existing scripts.** The status quo: slow and brittle, and the seeding differs per script. Rejected.
- **A debug menu inside the app.** Not scriptable, and it puts test code in the screens people review. Rejected.
- **Only `am instrument` tests.** Needs the test APK installed for every call and cannot be used for an interactive session. Rejected as the only channel; the tests keep using it.
- **Put the API in `debug` as well.** `debug` has the real app id, so it can sit on a phone next to a real vault. Rejected.

## Consequences
- **Better:** one scriptable surface for seeding, importing, waiting and reading results; the e2e runner, the screenshot job and manual testing stop duplicating setup code; a UI change no longer breaks the test drivers.
- **Worse, accepted:**
  - the QA build deliberately has a door that the real app does not. Anyone with adb on a QA phone can read and change its data. That is already true of QA (`SECURE_WINDOW` off, audio export on) and is why it never holds real data;
  - the API follows the app: each feature a test needs costs a command;
  - one more check in the build to keep it out of the release APK.
- **Still true:** the customer build is unchanged and never shows its screen to a screenshot; the real app on a shared phone is never touched.

## Verification
- **Build:** the release APK and merged manifest are checked for the API (provider, classes, strings) on every pull request, and the check fails if any is found.
- **JVM tests:** command parsing, the JSON shapes, the shell-user check, the locked-vault refusals, the refusal of data-deleting commands on a non-QA application id.
- **Device:** an instrumented test calls the provider as the shell user and as another app (refused). A seeded session run end to end through the API in the e2e runner.
