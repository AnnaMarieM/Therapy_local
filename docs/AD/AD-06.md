## Context

Facts from the code and from the tests of 2026-11-06 and 2026-11-07 (issue [#47](https://github.com/AnnaMarieM/Therapy_local/issues/47)):

- `models/Accelerators.kt` has had an `NPU` accelerator (priority 100, tried before the GPU) that was never available: LiteRT-LM reaches a Qualcomm NPU only through `libLiteRtDispatch_Qualcomm.so` plus the QNN libraries in the app's native library directory, and the `litertlm-android` AAR ships none of them.
- The dispatch library and the model file are tied to a Snapdragon generation. The tablet (SM-T970, SM8250) is not supported by LiteRT's Qualcomm backend. The phone (2510DPC44G, SM8750, Android 16) is.
- On the phone, with the libraries in the APK, LiteRT registers the NPU, loads `libQnnSystem.so` and `libQnnHtp.so` (SDK v2.50.0), opens `libQnnHtpV79Skel.so` over FastRPC and starts compiling Gemma 4 E2B (`gemma-4-E2B-it_NPU_Uncompiled.litertlm`). That compile ran out of memory on the phone and the engine process died with signal 6 after 57 s in `initialize` (`Scudo ERROR: internal map failure`). The guard struck the NPU and the app stayed up, as AD-01 intends. Hugging Face has no Gemma 4 file compiled for SM8750; an ahead-of-time build needs an x86_64 machine (the converter and the Qualcomm compiler plugin ship x86_64 wheels only; this host is aarch64).
- The official EmbeddingGemma file for SM8750 (`litert-community/embeddinggemma-2-740m-litert-lm`, `embeddinggemma-2-740m_Qualcomm_SM8750.litertlm`, 543,522,816 bytes, SHA-256 `ac1973c0195dc6e28a621651f2f5e04d35fdc7a7b11cdbbe94f29f5dccb57996`) exists. It has not yet been run on the phone (Verification).
- Runtime libraries, both from Maven, no Qualcomm login:
  - `com.google.ai.edge.litert:litert-npu-runtime-qualcomm:2.3.0` (Apache-2.0): the dispatch library and compiler plugin.
  - `com.qualcomm.qti:qnn-runtime:2.50.0` (Qualcomm AI Stack licence): the QNN/HTP runtime. Both must be one QAIRT version (2.50.0), the one the Gemma NPU bundles on Hugging Face were built with; a different pair gives "Unsupported context binary version".
- APK size: 73.7 MB before, 136.7 MB after the two libraries (`libQnnHtpPrepare.so` alone is 85 MB), with `libQnnGpu.so`, `libQnnDsp*.so` and the V68 skels excluded in `app/build.gradle.kts`. Measured on this build (`scripts/build.sh full` at the merge of origin/main a08ab84, arm64-v8a): QA APK 136,491,694 bytes (130.2 MiB, 136.5 MB), release (unsigned) 136,455,618 bytes, feel 136,463,606 bytes.
- The licence of `qnn-runtime-2.50.0.aar` is the file `LICENSE.pdf` in the artifact (the AAR also carries `NOTICE.txt` with third-party notices; AAR SHA-256 `b507656e4031d8aa6a7ab0fecf725b941096737ad7440ad7ea288f7c9cc9d743`). It does not allow distribution "on a standalone basis". The following applications are considered high-risk (the "High-Risk Applications"): (1) biometric identification (not otherwise considered an Unacceptable Risk Application); (2) critical infrastructure; (3) education and vocational training; (4) employment; (5) access to and enjoyment of essential private services and essential public services and benefits; (6) law enforcement; (7) migration, asylum, and border control management; (8) recommender systems of social media platforms; (9) administration of justice and democratic processes; and/or (10) any other AI system that when deployed, makes, or is a substantial factor in making, a consequential decision. ## Decision

Accepted on 2026-11-07 02:08 CET by Martin Hajný (@hajnina), with the APK size below.

1. **The NPU is used only on SoCs that we validated on hardware we own.** Every other device uses the GPU, then the CPU. There is no name-based or vendor-based rule beyond the catalogue. (Policy stated by Martin Hajný (@hajnina) on 2026-11-07 00:51 CET.)
2. **The model catalogue is where a validated SoC is recorded.** `ModelRegistry.BACKEND_BUILDS` holds `BackendBuild(modelId, accelerator, soc, spec, evidence)`: one file per accelerator, SoC and model, so a GPU-specific file fits the same way. A role keeps ONE model (AD-02); an accelerator may have its own file of it. An entry is added only with the on-device evidence it points to.
3. **A device without an entry gets a reason and the next backend.** `NpuRuntime.modelReason` writes a factual `backend_skipped` reason (`no validated NPU model for SM8250 (...; validated on SM8750)`, `NPU model file for SM8750 not downloaded (...)`, `NPU runtime library missing (...)`).
4. **A bundle is checked before the NPU runs it.** `NpuBundleCheck` (engine process) reads the bundle's own metadata and refuses one whose NPU brand is not Qualcomm or whose SoC is not the device's, with the facts, instead of failing in the driver.
5. **Downloads follow the catalogue.** `ModelSetup` fetches the NPU build only on a device that has an entry for its SoC; every other device downloads nothing extra.
6. **The runtime libraries ship in the APK**, as pinned Maven dependencies (`litert-npu-runtime-qualcomm:2.3.0`, `qnn-runtime:2.50.0`), one QAIRT version. The QNN GPU and DSP backends and the V68 skels are excluded.
7. **A failing NPU strikes only the NPU.** The engine process dies, the guard records it, the ladder goes on (AD-01). `NativeLogTail` adds the dead host's last native log lines to `engine_died`.
8. **QA only:** `MemProbeActivity` (prefill and decode tokens per second) and `EmbedProbeActivity` measure a backend without the pipeline.

Adding an optimised device: validate the model on the device (load, speed, memory, output compared with the CPU), put the result in the evidence, add a `BackendBuild` entry, add the SoC to the Verification table below in a new record that references this one.

Gemma 4 on the NPU is not part of this decision's first delivery: no SM8750 file exists yet and the on-device compile ran out of memory. It enters the catalogue only after a validated file exists.

## Alternatives considered

- **Try the NPU on every Qualcomm device.** Rejected: the dispatch library and the model file are per Snapdragon generation, a file for another chip fails inside the driver, and the tablet's SoC is unsupported. A failure there is a crash of the engine process on a therapist's device.
- **Decide by chip name or Android version without a catalogue.** Rejected: it says nothing about what we measured. The catalogue entry carries its evidence.
- **Download the QNN libraries on demand instead of shipping them.** Not chosen now: it needs a hosting place and a trust path for native code, and the licence permits distribution only "as incorporated in Your software application". Open for a later record if the APK size is not accepted.
- **Ship per-SoC APK splits.** Not chosen now: it adds a delivery channel. Also open for a later record.
- **Do not ship the NPU at all.** The alternative if the owner does not accept the licence clause or the APK growth; the GPU and CPU paths are unchanged.

## Consequences

Better:
- On a validated SoC, a model with an NPU file can run on the NPU (to be shown, see Verification).
- No device is sent to a backend we have not run.
- Each validated SoC has its measured evidence in the repository.

Worse, to be accepted by the owner:
- The APK grows from 73.7 MB to 136.7 MB (issue #47 figures); for this build: Measured on this build (`scripts/build.sh full` at the merge of origin/main a08ab84, arm64-v8a): QA APK 136,491,694 bytes (130.2 MiB, 136.5 MB), release (unsigned) 136,455,618 bytes, feel 136,463,606 bytes.
- The app redistributes Qualcomm's closed-source runtime, under the licence above, including the High-Risk Applications clause.
- Of the 85 MB `libQnnHtpPrepare.so`: it is the on-device graph compiler. flutter_gemma, which runs Gemma 4 on the NPU on a Galaxy S25, leaves it out and ships only ahead-of-time compiled models ([qnn_runtime.dart](https://github.com/DenisovAV/flutter_gemma/blob/main/packages/flutter_edge_ai_litertlm/lib/src/hook/qnn_runtime.dart): "libQnnHtpPrepare (on-device compilation only)"). We need it only for a `*_NPU_Uncompiled.litertlm` file; with AOT files it can be dropped, and the APK growth would be about 81 MB smaller. Not yet tested by us on the phone.
- Two more native dependencies that must be updated together (one QAIRT version).

Accepted, still true:
- On every device that is not an optimised device, behaviour is as before: GPU, then CPU.
