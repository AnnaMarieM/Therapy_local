## Context

Facts from the code and from the tests of 2026-11-06 and 2026-11-07 (issue [#47](https://github.com/AnnaMarieM/Therapy_local/issues/47)):

- `models/Accelerators.kt` has had an `NPU` accelerator (priority 100, tried before the GPU) that was never available: LiteRT-LM reaches a Qualcomm NPU only through `libLiteRtDispatch_Qualcomm.so` plus the QNN libraries in the app's native library directory, and the `litertlm-android` AAR ships none of them.
- The dispatch library and the model file are tied to a Snapdragon generation. The tablet (SM-T970, SM8250) is not supported by LiteRT's Qualcomm backend. The phone (2510DPC44G, SM8750, Android 16) is.
- On the phone, with the libraries in the APK, LiteRT registers the NPU, loads `libQnnSystem.so` and `libQnnHtp.so` (SDK v2.50.0), opens `libQnnHtpV79Skel.so` over FastRPC and starts compiling Gemma 4 E2B (`gemma-4-E2B-it_NPU_Uncompiled.litertlm`). That compile ran out of memory on the phone and the engine process died with signal 6 after 57 s in `initialize` (`Scudo ERROR: internal map failure`). The guard struck the NPU and the app stayed up, as AD-01 intends. Hugging Face has no Gemma 4 file compiled for SM8750; an ahead-of-time build needs an x86_64 machine (the converter and the Qualcomm compiler plugin ship x86_64 wheels only; this host is aarch64).
- The official EmbeddingGemma file for SM8750 (`litert-community/embeddinggemma-2-740m-litert-lm`, `embeddinggemma-2-740m_Qualcomm_SM8750.litertlm`, 543,522,816 bytes, SHA-256 `ac1973c0195dc6e28a621651f2f5e04d35fdc7a7b11cdbbe94f29f5dccb57996`, checked against Hugging Face) does not load with `litertlm-android` 0.18.1 on the phone (Verification). It is therefore not in the catalogue.
- The official prebuilt Gemma 4 E2B file for SM8750 (`litert-community/gemma-4-E2B-it-litert-lm` at revision `fc978c656bfaecebc54c31ccb9a2db7750ef6920`, `gemma-4-E2B-it_qualcomm_sm8750.litertlm`, 2,724,793,461 bytes, SHA-256 `248e732911222c173d6c7d7086258990fc009f23a6144fb8abcf43dd111c7a1b`, QAIRT v2.50.0.260828) loads and runs on the phone's NPU (Verification). ## Decision

Accepted on 2026-11-07 02:08 CET by Martin Hajný (@hajnina), with the APK size below.

1. **The NPU is used only on SoCs that we validated on hardware we own.** Every other device uses the GPU, then the CPU. There is no name-based or vendor-based rule beyond the catalogue. (Policy stated by Martin Hajný (@hajnina) on 2026-11-07 00:51 CET.)
2. **The model catalogue is where a validated SoC is recorded.** `ModelRegistry.BACKEND_BUILDS` holds `BackendBuild(modelId, accelerator, soc, spec, evidence)`: one file per accelerator, SoC and model, so a GPU-specific file fits the same way. A role keeps ONE model (AD-02); an accelerator may have its own file of it. An entry is added only with the on-device evidence it points to.
3. **A device without an entry gets a reason and the next backend.** `NpuRuntime.modelReason` writes a factual `backend_skipped` reason (`no validated NPU model for SM8250 (...; validated on SM8750)`, `NPU model file for SM8750 not downloaded (...)`, `NPU runtime library missing (...)`).
4. **A bundle is checked before the NPU runs it.** `NpuBundleCheck` (engine process) reads the bundle's own metadata and refuses one whose NPU brand is not Qualcomm or whose SoC is not the device's, with the facts, instead of failing in the driver.
5. **Downloads follow the catalogue.** `ModelSetup` fetches the NPU build only on a device that has an entry for its SoC; every other device downloads nothing extra.
6. **The runtime libraries ship in the APK**, as pinned Maven dependencies (`litert-npu-runtime-qualcomm:2.3.0`, `qnn-runtime:2.50.0`), one QAIRT version. The QNN GPU and DSP backends and the V68 skels are excluded.
7. **A failing NPU strikes only the NPU.** The engine process dies, the guard records it, the ladder goes on (AD-01). `NativeLogTail` adds the dead host's last native log lines to `engine_died`.
8. **A bundle that carries no NPU metadata is not refused.** The official EmbeddingGemma file reports brand `UNKNOWN` and no SoC on every modality; `NpuBundleCheck` refuses only a bundle whose metadata says another brand or another SoC.
9. **QA only:** `MemProbeActivity` (prefill and decode tokens per second) and `EmbedProbeActivity` measure a backend without the pipeline.

Adding an optimised device: validate the model on the device (load, speed, memory, output compared with the CPU), put the result in the evidence, add a `BackendBuild` entry, add the SoC to the Verification table below in a new record that references this one.

The first catalogue entry is Gemma 4 E2B on SM8750 with the official prebuilt file above (the on-device compile of the `_NPU_Uncompiled` file ran out of memory; the prebuilt file does not need it). The EmbeddingGemma SM8750 file has no entry: it failed on the phone.

## Alternatives considered

- **Try the NPU on every Qualcomm device.** Rejected: the dispatch library and the model file are per Snapdragon generation, a file for another chip fails inside the driver, and the tablet's SoC is unsupported. A failure there is a crash of the engine process on a therapist's device.
- **Decide by chip name or Android version without a catalogue.** Rejected: it says nothing about what we measured. The catalogue entry carries its evidence.
- **Download the QNN libraries on demand instead of shipping them.** Not chosen now: it needs a hosting place and a trust path for native code, and the licence permits distribution only "as incorporated in Your software application". Open for a later record if the APK size is not accepted.
- **Ship per-SoC APK splits.** Not chosen now: it adds a delivery channel. Also open for a later record.
- **Do not ship the NPU at all.** The alternative if the owner does not accept the licence clause or the APK growth; the GPU and CPU paths are unchanged.

## Consequences

Better:
- On a validated SoC, Gemma 4 E2B runs on the NPU about 2.4 times faster at decode and about 14 to 30 times faster at prefill than on the CPU (Verification, one phone).
- No device is sent to a backend we have not run.
- Each validated SoC has its measured evidence in the repository.

Worse, to be accepted by the owner:
- The APK grows from 73.7 MB to 136.7 MB (issue #47 figures); for this build: Measured on this build (`scripts/build.sh full` at the merge of origin/main a08ab84, arm64-v8a): QA APK 136,491,694 bytes (130.2 MiB, 136.5 MB), release (unsigned) 136,455,618 bytes, feel 136,463,606 bytes.
- The app redistributes Qualcomm's closed-source runtime, under the licence above, including the High-Risk Applications clause.
- `libQnnHtpPrepare.so` (85 MB) is Qualcomm's on-device graph compiler. flutter_gemma, which runs Gemma 4 on the NPU on a Galaxy S25, leaves it out and ships only ahead-of-time compiled models ([qnn_runtime.dart](https://github.com/DenisovAV/flutter_gemma/blob/main/packages/flutter_edge_ai_litertlm/lib/src/hook/qnn_runtime.dart): "libQnnHtpPrepare (on-device compilation only)"). Whether the official prebuilt files still need it here is not established (Verification): the owner accepted the APK size with it included.
- Two more native dependencies that must be updated together (one QAIRT version).

Accepted, still true:
- On every device that is not an optimised device, behaviour is as before: GPU, then CPU.

**EmbeddingGemma 2 740M, official SM8750 file: does not work** (`EmbedProbeActivity`, `--es backend NPU --ez force true`, logs `ep_npu3_logcat.txt`):
- The NPU was reached (LiteRT registered the NPU, loaded `libQnnSystem.so`/`libQnnHtp.so`, SDK v2.50.0, opened FastRPC to the DSP) and failed in `EmbeddingEngine.initialize`: `QNN op validation failed: 'Gather_5' (type=Gather)` for the `EmbeddingLookup` op ("not supported in Qualcomm Compiler"), then `Input tensor 2 lacks data`, `Failed to invoke the compiled model`. The ladder struck the NPU and the embedder loaded on the CPU (`backend` in the result JSON: CPU).
- So there is no NPU load time, call time, peak memory or cosine to the CPU reference for the embedder. The golden proof (`EmbedGolden`, cosine at least 0.98) was never reached.
- CPU reference runs: load 620 ms and 546 ms; per call 56 to 96 ms (first run), 70 to 178 ms (second); the CPU fallback in the NPU runs gave 62 to 81 ms.
- Cause not established. Evidence gathered afterwards (research only; the phone was not connected, so nothing was run):
  - The file was updated on Hugging Face on 2026-11-06 22:09 UTC, after `litertlm-android` 0.19.0 (2026-11-02) and 0.19.1 (2026-11-05) were released; the app uses 0.18.1 (2026-10-20). `strings` on the file shows `min_runtime_version` 2.22.0 and embedded QAIRT builds v2.49.0.260730 and v2.50.0.260828. Maven has `litertlm-android` 0.19.0 and 0.19.1 and `litert-npu-runtime-qualcomm` 2.3.2. A runtime that is too old for the file is the leading hypothesis, not a finding.
  - LiteRT-LM `main` fixed related embedding-engine problems on 2026-11-06 (3e24a714, "Read the embedding text encoder's external weights into host memory on CPU", issue 4045), after the 0.19.1 tag. I found no issue with the `Gather`/`EmbeddingLookup` rejection or `Input tensor 2 lacks data`.
  - flutter_gemma runs EmbeddingGemma 2 on Qualcomm NPUs through `EmbeddingEngine`, but with the 270M text bundles (SM8650, QCS8275; its own comment, `embeddinggemma2_npu_test.dart`), and reports that NPU vectors sit apart from the CPU's (cosine to the CPU golden mean 0.83, min 0.787). Our proof threshold is 0.98 (`EmbedGolden.MIN_COSINE`), so even a loading NPU embedder is likely to be refused by the proof.
  - Hugging Face has `embeddinggemma-2-text-270m_Qualcomm_SM8750.litertlm` (text only, repo last modified 2026-10-06). The app's embedder is the 740M with audio; using the 270M would be a different model and vector space (AD-02, one model per role) and is not part of this record.
  - Experiments run on 2026-11-07 on the phone (local branch `experiment/embedgemma-npu-runtime`, pushed as WIP, not part of this branch): 1) `litertlm-android` 0.19.1 with `litert-npu-runtime-qualcomm` 2.3.0; 2) the same with 2.3.2. Both fall back to the CPU. With 0.19.1 the LiteRT inside looks for `LiteRtDispatchQueryInterface` and `LiteRtCompilerPluginQueryInterface` in the Qualcomm libraries and logs `undefined symbol` and `No usable Dispatch runtime found`; the Maven libraries (2.3.0 and 2.3.2, the newest published) export only the older `LiteRtDispatchGetApi` and `LiteRtCreateCompilerPlugin`. The error moved from the EmbeddingLookup rejection (0.18.1) to `Failed to allocate tensors` (0.19.1). The golden cosine was therefore never reached and there is no NPU speed for the embedder. A matching dispatch library and compiler plugin built from the LiteRT source of 0.19.1, or a newer Maven artifact, would be needed; the 0.83 mean cosine reported by flutter_gemma for the 270M suggests the 0.98 proof may still refuse the NPU. Logs: `.bigcache/npu/logs-2026-11-07/ep_e1_npu_logcat.txt`, `ep_e2_npu_logcat.txt`. A third experiment was not run: nothing in the evidence suggested one.
- Before the bundle check was changed, the check refused this file because it reports no NPU metadata (`npu_brand=UNKNOWN`, `bundle_soc=null`, on all four modalities).

**Other checks**
- A failing NPU load strikes only the NPU: seen for the embedder above (app and `:batch` host stayed up, CPU loaded next).
- `libcdsprpc.so` / `extractNativeLibs`: the merged manifest of the QA APK already contains `uses-native-library libcdsprpc.so` (it comes from the manifest of `litert-npu-runtime-qualcomm`) and `extractNativeLibs`; the phone log shows `libcdsprpc.so loaded` and an opened FastRPC session. Nothing was changed.
- `libQnnHtpPrepare.so`: the Gemma file is ahead-of-time compiled, but loading it still runs LiteRT's compiler plugin on the device for small parts (log: `JIT compilation changed model, reserializing`, `Generating context binary`). Whether that path loads `libQnnHtpPrepare.so` was not tested (removing it is a packaging change). The earlier statement that precompiled models do not need it is therefore not confirmed.
- Not measured: the tablet; a release build on the phone; the Gemma file inside the real pipeline (a session end to end); thermal behaviour over a long run; the NPU while the `:live` host runs; windows over 3,000 tokens.
