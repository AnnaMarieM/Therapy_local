# AD-08: The GPU and NPU are tried every time; no free-memory gate

| | |
|---|---|
| Status | Accepted |
| Decided | `2026-11-11 00:01 CET` |
| Decided by | Martin Hajný (@hajnina) |
| Drafted by | Claude (Sonnet), branch `feature/gpu-no-memory-gate` |

## Context
- [AD-01](AD-01.md) puts every model in its own process (`:live`, `:batch`) so that a GPU driver crash or a kill by the low-memory killer ends only that process. The guard (`BackendGuard`) learns from what happens and the ladder falls back to the CPU.
- On top of that, every GPU/NPU load had a free-memory gate (`LlmMemory.gate`): the model's size plus 1 GiB, and for the embedder a cost estimate by input size plus 1 GiB, had to be free and the system must not report low memory. Otherwise the backend was skipped without being tried.
- Measured 2026-11-10 on the POCO F8 Pro (11 GB), QA build, `gemma-4-e4b`: the gate wanted 4,514 MB and saw 3,547 MB free, so E4B ran on the CPU. With the gate lifted (`MemProbeActivity --ez force true`, GPU) it loaded in 31.8 s, passed both proofs and answered twice without a crash. Free memory fell to about 1.7 GB and the app stayed up. The gate was refusing a load that works.
- The gate guessed at a number the engine process is there to find out. It cost a working accelerator on a phone that can run it, and "free memory now" is a poor predictor: Android reclaims cached memory when asked.

## Decision
1. **A GPU/NPU load is never skipped for lack of free memory.** `LlmMemory.gate`, `gateForCost`, `gpuNeeds`, `MemoryConfig.GPU_MEMORY_FACTOR`, `GPU_HEADROOM_BYTES`, `EMBED_GPU_*`, `embedGpuCostBytes` and `Accelerator.takesSystemMemory` are removed.
2. **The only reason to skip a backend before trying it is that its runtime is missing** (`Accelerators.unavailable`, e.g. `libLiteRtDispatch_Qualcomm.so`), and the guard's block or demotion after real failures.
3. **Free memory is still logged** (`LlmMemory.available`, `backend_phase`, `backend_open_slow`) so a kill can be read afterwards. It decides nothing.
4. The embedder is still opened at the smallest input size that holds the need (`EmbeddingConfig.INPUT_SIZES`), not at 8192: that is sizing, not a gate. Measured on the Galaxy Tab S7 (2026-11-07), 4096 and 8192 made lmkd kill `:live` while loading.

## Alternatives considered
- **Lower the threshold (headroom or factor).** Still a guess; any number is wrong on some phone.
- **Gate only the LLM, not the embedder.** The same argument applies, and the two would disagree.
- **Keep the gate and add a "try GPU anyway" setting.** Hides the default behaviour behind a switch nobody sets; the engine process exists to take this risk.

## Consequences
- Better: the GPU is tried on every phone and every load. E4B can use the GPU on an 11 GB phone.
- Worse: a load that does not fit can now be killed by the low-memory killer. That ends `:live` or `:batch` only ([AD-01](AD-01.md)), costs a strike, and the next backend is tried; after the block threshold (2 strikes, or 3 once proven) the guard stops trying the GPU on that phone until **Test everything again** or an update. The GPU can then still be skipped, by the guard, not by free memory.
- Accepted, still true: no device name, SoC or total-RAM tier takes part in any choice.

## Verification
- Unit tests: the ladder no longer has a memory reason; the gate tests are removed.
- Device: POCO F8 Pro, QA build, E4B loads on the GPU through the normal ladder (auto, no force) with about 3.5 GB free.
