# AD-13: CI is built for wall-clock time: maximum parallelism, no loss of test robustness

| | |

## Context
- Waiting for CI is the slowest part of development. Over the M1 work, PRs sat for hours on red or pending checks, and every merge waited for a full run.
- One measured green run of `ci.yml` (run 43075199451) took about 13 minutes. `build` ran alone for about 5 minutes (one `scripts/build.sh` step of 290 s: the Gradle build and the JVM unit tests), and only then did the emulator lanes start. The slowest lane (`android-test`, `pixel_tablet`) took 463 s, of which 88 s was creating an AVD that should have come from the cache.
- A cold apt step in the builder once turned `build` red without any code fault (`apt-get` exit 100).
- CI runs on GitHub's free runners. Compute and minutes are not a constraint we care about; wall-clock time is.
- The tests are what make fast, mostly agent-driven changes safe. They cover the engine processes, the vault and the data layer, and several of them can only be run on an emulator.

## Decision
1. **CI is optimised for wall-clock time from push to a verdict.** Anything that can run at the same time runs at the same time: independent jobs do not wait for each other, and a long job is sharded as far as it helps.
2. **A job depends only on what it needs.** An emulator lane needs the APK, not the unit tests; unit tests do not wait for emulators. A single serial job that every other job waits on is a defect to fix.
3. **Cache what is rebuilt on every run:** Gradle, the builder image and its packages, and the emulator snapshot (restored on every PR, which means it is also saved on `main`). A cache miss that repeats is a bug.
4. **Retry steps that fail for reasons outside the code** (package mirrors, network, emulator startup) so that a red check means the code is wrong.
5. **Robustness is not traded for speed.** Speed is never bought by dropping, loosening, sampling, skipping or reordering a test so that it no longer gates a merge, by lowering a timeout or a threshold, or by replacing a device or emulator with something weaker. Removing or weakening a check is a separate decision with its own AD. Paths that skip a job (for example, docs-only changes) are allowed only where the skipped job cannot be affected by the change.
6. **The only limit on parallelism is GitHub's concurrent-job cap for the plan.** Jobs per run are sized so that one run fits under the cap with headroom, since runs of different PRs share it.
7. **New CI work follows this rule.** A new job or test is placed so it runs beside the others, and a change that lengthens the critical path says so and why.

## Alternatives considered
- **Run only a smoke subset on PRs, the full suite on `main` or nightly.** Rejected as the default: it moves failures from the PR to after the merge, which is the opposite of robust. It may be reconsidered for a specific test by a later decision.
- **Keep CI as it is and run tests locally before pushing.** Rejected as the only measure. Local runs are already done where possible, but the ARM laptop cannot run the emulator tests, so CI is the only verification for them.
- **Pay for larger or self-hosted runners.** Rejected for now: the delay is in the shape of the job graph and in cache misses, not in raw runner speed.

## Consequences
- **Better:** a shorter time from push to merge; fewer false reds; a shape of the workflow that stays fast as tests are added.
- **Worse, accepted:** more jobs and shards per run, so more cache and artifact handling, more failing jobs to read in a bad run, and a workflow file that is harder to follow; more runner minutes.
- **Still true:** every check that gated a merge before still gates it, on the same devices and with the same thresholds.

## Verification
- **Review:** a change to `.github/workflows/` shows the critical path before and after (job durations from a run on the branch) and states which checks it touches.
- **Measurement:** per-job and per-step durations from `gh api repos/AnnaMarieM/Therapy_local/actions/runs/<id>/jobs`. The first change under this decision is the CI speed-up PR.
