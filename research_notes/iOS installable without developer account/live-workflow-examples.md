# Live GitHub-Actions examples: unsigned IPA → installable OTA install, free Apple ID context

Researched & verified live on 2026-11-16 via GitHub API (`gh api repos/…/actions/runs`, `gh api repos/…/contents/.github/workflows`) and by downloading released IPAs and reading their embedded provisioning profiles. All run dates below are from the runs API (UTC). Verification standard applied: repo exists + workflow file read + at least one successful Actions run in roughly the last 12–18 months.

## Key Question 1 — Which CI authentication pattern do working projects use for free-account signing?

### Takeaway
Every verified working project uses pattern (a): the user supplies a `.p12` (certificate + private key, base64 or committed cert-pack) plus a `.mobileprovision` containing their device UDID, and the workflow signs with `codesign` (macOS runner), `zsign` (macOS or Linux runner), or `rcodesign` as fallback. Headless Apple ID login (pattern b) exists and works only for paid accounts (fastlane `spaceauth` with 2FA relayed through a web UI, or stored `FASTLANE_SESSION`); nothing public shows free-account headless provisioning working unattended, and SignTools explicitly dropped free accounts.

### Cited Findings

**Pattern (a) — user-exported p12 + mobileprovision as repo secrets / cert packs — is the only pattern with live green runs.**
- The SignTools-CI builder is a thin GitHub Actions wrapper: `.github/workflows/sign.yml` on `macos-26`, two secrets (`SECRET_URL`, `SECRET_KEY`), runs `./sign.py` — [SignTools/SignTools-CI/.github/workflows/sign.yml](https://github.com/SignTools/SignTools-CI/blob/master/.github/workflows/sign.yml). `sign.py` is 1,310 lines of fastlane + `security` keychain automation ([sign.py](https://github.com/SignTools/SignTools-CI/blob/master/sign.py)).
- SignTools-CI's README: "Starting from SignTools 3.0, free developer accounts are no longer supported." — [SignTools-CI README](https://github.com/SignTools/SignTools-CI#note-on-free-developer-accounts).
- `sign.py` does headless Apple ID login by running `fastlane spaceauth --copy_to_clipboard` with `FASTLANE_USER`/`FASTLANE_PASSWORD` env vars, and pulls the 2FA code from the self-hosted SignTools web service (`GET {secret_url}/jobs/{job_id}/2fa`), i.e. a human must be present at the service UI during the run — [sign.py, fastlane_auth()](https://github.com/SignTools/SignTools-CI/blob/master/sign.py).
- The old `SignTools/ios-signer-service` URL now resolves to [SignTools/SignTools](https://github.com/SignTools/SignTools) (renamed/absorbed); the current CI builder is [SignTools-CI](https://github.com/SignTools/SignTools-CI), pushed 2026-11-11, not archived (repo API).
- Stale third-party "builders" for the old service: [sayed001/SayedIPAs](https://github.com/sayed001/SayedIPAs) (SignTools-CI fork template, `.github/workflows/sign.yml`, `macos-latest`) and [TNT599/SignIOS](https://github.com/TNT599/SignIOS) — both show **0 successful workflow runs** (runs API).
- Pattern (b) in its "stored session cookie" form exists on CI but only in paid App Store/TestFlight flows, e.g. `FASTLANE_SESSION: ${{ secrets.FASTLANE_SESSION }}` in [standardnotes/app ios.testflight.yml](https://github.com/standardnotes/app/blob/main/.github/workflows/ios.testflight.yml) (GitHub code search for `FASTLANE_SESSION path:.github/workflows`, 7 hits, all paid-portal flows).
- `xcodebuild -allowProvisioningUpdates` without an App Store Connect API key does not resolve profiles on CI: [varunsalian/debrify build.yml](https://github.com/varunsalian/debrify/blob/main/.github/workflows/build.yml) carries the comment that `-allowProvisioningUpdates` "cannot resolve a profile on a [runner]"; every other hit in GitHub code search pairs `-allowProvisioningUpdates` with `-authenticationKeyPath/ID/IssuerID` (ASC API key = paid team) — e.g. [AssiamahS/hablo ci.yml](https://github.com/AssiamahS/hablo/blob/main/.github/workflows/ci.yml), [ente/ente cast-build.yml](https://github.com/ente/ente/blob/main/.github/workflows/cast-build.yml).
- GitHub code search for `Xcode-Token path:.github/workflows` (restoring Xcode's Apple ID keychain session to a runner) returns **zero** results — no public repo does the "keychain restore of Xcode's account session" trick.
- Pattern (c), SignTools 4 (service + builder): the service is self-hosted anywhere; builders are [SignTools-CI](https://github.com/SignTools/SignTools-CI) (CI providers: GitHub Actions macOS runners, Semaphore) or [SignTools-Builder](https://github.com/SignTools/SignTools-Builder) ("Sign iOS apps on demand using your own Mac", pushed 2026-11-16). There is no GitHub-runner-hostable variant beyond SignTools-CI, and per its README it does not support free accounts — [SignTools README](https://github.com/SignTools/SignTools) ("A free, self-hosted platform…", features list "Provisioning profiles and developer accounts supported").
- A SignTools-4-style architecture fully inside GitHub exists: [MaliceKy/ipa-signer](https://github.com/MaliceKy/ipa-signer) (no external service at all) and [suleyman13900/SignHub](https://github.com/suleyman13900/SignHub) (external broker, GitHub runner as worker — currently failing, see Q2).
- Pattern (d), `rcodesign` (Rust `apple-codesign` from indygreg/apple-platform-rs) as the signer: [mirazbakis/AltLoad sign-ota.yml](https://github.com/mirazbakis/AltLoad/blob/main/.github/workflows/sign-ota.yml) installs pinned `rcodesign` 0.29.0 with SHA-256 check and uses it to sign with **revoked or expired** identities, which Apple's `codesign` refuses — directly relevant to free 7-day certs.

### Inferences
- For the consumer project (free Apple ID, one Mac, private repo, CI-built unsigned IPA), the realistic flow is exactly pattern (a): on their Mac in Xcode, let the free Apple ID mint the "Apple Development" cert and the free team profile with the phone's UDID (Xcode → Preferences → Accounts, or `~/Library/MobileDevice/Provisioning Profiles`), export the p12 from Keychain Access, then store both (base64) as repo secrets and sign in CI with zsign/codesign/rcodesign. Every verified workflow below accepts whatever p12+profile pair you give it, so a free-team pair works mechanically the same as a paid one.
- Free personal-team certs/profiles expire in 7 days, so the secrets must be re-exported weekly and CI re-run weekly — AltLoad's weekly re-sign cron (Mon 04:17 UTC) shows the operational cadence to copy.

### Gaps
- **No public repo shows a green CI run with a verifiably FREE personal-team certificate.** Free-team users keep repos private, and a p12+profile is team-agnostic to the workflow, so free-vs-paid cannot be distinguished from workflow files alone. AltLoad's committed cert packs turned out to be paid/enterprise certs (see Q2), and mangayomi/AnymeX's released IPAs carry expired enterprise profiles. The free-account claim rests on mechanism-level compatibility + SignTools' documented free-account withdrawal, not on a public free-cert green run.

### Inferences
- The OTA half has two proven hosting choices: **GitHub Pages** (AltLoad, hablo/AssiamahS fleet, Asspp, Termix) — the safe default — and **GitHub Releases** (MaliceKy, EhViewer prints manifest URL for its own server). Releases-hosted manifests are served as `application/octet-stream`; several projects avoid it, and the safest observed pattern is manifest + IPA both on Pages. Termix adds a practical constraint: no query strings in the manifest URL.
- Two signing-engine choices are proven on hosted runners: Apple `codesign` in a throwaway keychain on macOS (AltLoad, Asspp, ShadersCamera, EhViewer) and **zsign on a Linux runner** (MaliceKy on `ubuntu-latest`, SignHub on `macos-14` builds zsign, mangayomi/AnymeX use zsign's prebuilt macOS binary). zsign accepts expired/revoked certs silently; AltLoad's `rcodesign` fallback exists precisely because Apple `codesign` refuses dead identities.
- For `com.therapylocal.app` (device-family iOS, existing unsigned IPA from CI), the closest copy targets are AltLoad's `sign-ota.yml` + `signing/scripts/*.sh` (macOS, robustness features included: legacy-p12 fallback, profile→bundle-id inference, per-slot manifests, weekly cron, Pages deploy) or MaliceKy's `sign-ipa.yml` (Linux runner, secrets-only, Releases OTA). AltLoad's scripts are the most production-quality of the set.
- AltLoad committing real certs publicly (31 packs, `password.txt` with the password inside the repo) is a hygiene anti-pattern; for the private consumer repo, the same scripts should read `P12_BASE64`/`MOBILEPROVISION_BASE64` secrets instead (as MaliceKy and Asspp do).

### Gaps
- No candidate publishes a green run that demonstrably installed over OTA from the produced link (installation happens on private devices and leaves no public trace). Verification is: workflow green + OTA assets produced + (for mangayomi/AnymeX) artifact inspected. The OTA-manifest format itself is standard (`itms-services://?action=download-manifest&url=<https manifest>`) and identical across all of them.
- Whether Safari will accept a manifest.plist served from `github.com/*/releases/download/…` (MaliceKy's choice) could not be confirmed from public evidence; community practice favors Pages.

## Key Question 3 — Specific leads checked (SignTools, ios-signer-service, zsign forks, marketplace, AltStore PAL)

### Takeaway
The SignTools organization is alive and split into the self-hosted service (SignTools 4), a Mac-based builder (SignTools-Builder), and a CI builder (SignTools-CI) that runs on GitHub macOS runners but is documented as paid-accounts-only. The old `ios-signer-service` name is gone (redirects into SignTools/SignTools). The maintained zsign is `zhlynn/zsign` (v0.7 prebuilt macOS binaries; used by mangayomi/AnymeX/Termix-fleet), with Rust ports `jveko/zsign-rs` and `nab138/zsign-rust` active. No dedicated "free Apple ID" Marketplace action survived verification.

### Cited Findings
- SignTools org repos (org API, 2026-11-16): `SignTools` (service, pushed 2026-11-16, "A free, self-hosted platform to sideload iOS apps without a computer"), `SignTools-CI` (pushed 2026-11-11, not archived), `SignTools-Builder` (pushed 2026-11-16, "using your own Mac"), `altserver-cert-dumper` (2023, archived — the old free-account era tool that dumped AltServer's developer certificate on Windows), `ios-app-signer`/`XReSign` (archived macOS signing apps), `ota-me`/`ota-proxy` (2021, archived dummy-manifest servers).
- The free-account era is over upstream: SignTools-CI README "Note on free developer accounts: Starting from SignTools 3.0, free developer accounts are no longer supported" — [README](https://github.com/SignTools/SignTools-CI#note-on-free-developer-accounts).
- SignTools 4's architecture requires one macOS builder somewhere: service web UI for uploads; builder does the actual Apple-official codesigning; OTA install is served from the service — [SignTools README](https://github.com/SignTools/SignTools). For the consumer (who owns one Mac), `SignTools-Builder` on their own Mac + the service hosted free-tier is a viable non-CI alternative, but it's out of the GitHub-runner scope.
- zsign: original/maintained upstream is [zhlynn/zsign](https://github.com/zhlynn/zsign) — publishes `zsign-v0.7-macos-x64.zip` release assets that mangayomi/AnymeX curl in CI, and its `build/linux` makefile is what MaliceKy and SignHub compile on runners. Its own repo has `build.yml` building a musl static binary — [zhlynn/zsign/.github/workflows/build.yml](https://github.com/zhlynn/zsign/blob/main/.github/workflows/build.yml). Active Rust re-implementations found in code search: [jveko/zsign-rs](https://github.com/jveko/zsign-rs) and [nab138/zsign-rust](https://github.com/nab138/zsign-rust).
- GitHub Marketplace-style "sign without paid certs" actions: the searches surfaced no maintained, free-account-specific action; the recurring generic pattern is repos importing `apple-actions/*` or hand-rolled `security import` + `codesign`/zsign steps. The closest marketplace-adjacent reusable pieces are AltLoad's `signing/scripts/` shell scripts (sign-pack.sh / resign.sh / build-manifest.sh / build-site.sh) which are plain files meant to be copied.
- AltStore PAL: not applicable — it is an EU-only marketplace requiring paid developer infrastructure; no CI OTA pattern beyond what AltStore/SideStore already do on-device. SideStore/AltStore ecosystems did not surface a GitHub-hosted free-cert signing workflow in this round (their IPAs are built unsigned in CI and signed on-device/with AltServer).
- `nab138/iloader` ("User friendly sideloader", 5k★, green runs 2026-11-16) has a `build.yml` whose signing path (`DEV_ID_P12_BASE64`/`DEV_IDENTITY_NAME`) is conditional on secrets being set; its public releases do not demonstrate free-cert CI signing. Included as a pointer, not a verified example.

### Inferences
- "SignTools style, but GitHub-runners-only" is a real, working architecture — MaliceKy/ipa-signer implements it entirely with GitHub primitives (Pages/Actions/Releases + workflow_dispatch as the job queue, `run-name` as correlation id), and SignHub implements it with an external broker (and is currently failing). If the consumer ever wants a phone-triggered signer, MaliceKy's repo is a live blueprint; for a simple push→install pipeline, the direct pattern (a) workflows are less moving parts.
- The 7-day free-profile expiry makes any monthly-cadence setup useless; every free-account pipeline needs a weekly human step (re-export on the Mac) regardless of signing engine. AltLoad's cron + "Slots" model shows how to make that tolerable (drop a fresh pack into the repo, cron re-signs everything).

### Gaps
- I could not verify any SignTools-CI user fork end-to-end (forks are private by design — the README tells users to make the fork private). Evidence that the pipeline still works in 2026 is indirect: repo pushed 2026-11-11, dependabot/scheduled runs green, and the project is actively maintained. Issue-tracker threads specifically confirming "still works with GitHub Actions in 2025/2026" were not located within the call budget.
- AltStore PAL relevance was assessed from project descriptions only; no deep dive was done since it is EU/paid.

### Inferences
- The ecosystem's graveyard is consistent: everything built around free accounts died when Apple's free endpoints changed (SignTools 2→3 era, 2021–2022), and everything still green today either (i) takes a user-supplied p12+profile pair (pattern a) or (ii) is a paid-account fastlane/ASC pipeline. There is no maintained free-account-specific action or service.
- "0 successful runs" is a strong, cheap signal — three of the five dead leads had zero green runs ever, which the runs API exposes in one call. Any candidate should be gate-checked that way before reading its YAML.

### Gaps
- Run-failure reasons for SignHub (broker down? workflow bug?) were not diagnosed — only the conclusion codes were checked.
- The ~9 unverified OTA-manifest leads in the table above are listed as leads; each would need one runs-API call to promote to verified.
